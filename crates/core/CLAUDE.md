# crates/core

Area: the config model, routing, MCP rendering and `platform.rs`, with the rules for how MCP servers reach an agent and how a folder resolves to a profile. Moved out of the root `CLAUDE.md`.

## How MCP servers reach an agent (`crates/core/src/mcp.rs`)

- **No gateway or daemon.** On every save the app renders, per profile and per agent with an MCP descriptor, one config file per server in the agent's dialect plus a `launch.json` manifest (a dialect that is an argument, Codex's, writes no server file: `mcp::codex_table` renders the server as the `--config=mcp_servers.<name>={…}` argument itself, so `mcp/<id>/codex/` holds only `launch.json` and `stdio/`), under `~/.envrouter/mcp/<profile id>/<command>/` (files 0600, folder 0700). The shim reads only the manifest and adds its arguments ahead of the user's own. A save removes a manifest it no longer renders at once, but a server file, or a stdio spec (`stdio/<name>.json`, below), only 10 minutes after it stopped being named (`mcp::RETIRED_GRACE`, timed in `~/.envrouter/mcp-retired.json`), at a later save: a run that read the old manifest just before the save opens that file as the agent starts. For a spec it is longer-lived than that: an agent reruns the launcher at every reconnect, so a server removed or renamed more than 10 minutes ago fails a later reconnect of a session that began before the save, with the launcher's "is gone, restart the agent" line; a rotated secret applies at the server's next start without restarting the agent.
- **Always the `--flag=value` form.** Claude's `--mcp-config` and `--disallowedTools` take several values, so `--mcp-config <file>` as two arguments swallows the next one (`claude --mcp-config f mcp --help` breaks; `--mcp-config=f mcp --help` works, verified on 2.1.303). `config::validate` rejects a descriptor without the `=`. `claude mcp list` never shows flag-injected servers. Copilot (verified on 1.0.98) takes `--additional-mcp-config=@<file>` (repeatable, added to the user's own servers) and turns a tool off with one `--deny-tool=<server>(<tool>)` per tool; `copilot mcp list` doesn't show injected servers either. Copilot expands `${VAR}` in env and headers, not args (and passes a local server only `PATH`), which is why a stdio server's secrets never go through the agent's expansion at all: the launcher fills them in. Only a remote server's header secrets are still `${ENVROUTER_SECRET_<ID>}` for the agent to expand. **Codex** (verified against the 0.164.0 source) takes `--config=mcp_servers.<name>={…}`, global and one value per flag, so it can't swallow the next argument; it parses the value as `_x_ = <value>` and, if that fails, takes the text as a string, which fails its config load on every run, so `mcp::toml_str` writes exact TOML 1.0 basic strings (Codex uses `toml` 0.9, so no 1.1 escapes or multi-line inline tables) and a test parses every rendered argument as Codex does. Field names are bare and map keys always quoted; a stdio server with a secret is the helper's `exec` with `startup_timeout_sec = 50` (the store's 20 s plus Codex's 30 s default); a remote server's secret header is `env_http_headers`, which names `ENVROUTER_SECRET_<ID>` for Codex to read from its environment; disabled tools are `disabled_tools` inside the table (`denyArg` is null); an SSE server is left out (`McpDialect::takes`); only fields 0.164.0 knows are written, so `--strict-config` accepts them; `codex_apps` and `codex_tui` are refused as server names while an agent with the dialect is configured (`McpDialect::reserved_names`). Costs, all accepted: a value not in the store is on Codex's command line; any override makes the TUI, `resume` and `fork` run embedded instead of on Codex's shared background server, `queue` refuses to run that way, and `archive`, `unarchive`, `delete` and `remote-control` would write session state through a second server or run in the foreground, so those five are the registry's `skipSubcommands` for Codex (re-sweep on a new release; Codex reads a subcommand past its global options too, `codex -C ~/proj queue`, so its `optionsBeforeSubcommand` names the options that take a value, from 0.164.0's clap definitions: `takeOne`, and `takeMany` for `-i`/`--image`, which takes words up to the next one starting with `-`, and the shim steps past them, #187); and Codex deep-merges the server into one of the same name in its own `config.toml`, so the same transport merges (ours win) and a different one fails every command that loads config in that folder (`url is not supported for stdio`). Library names are kept, and `crates/ops/src/mcp_clash.rs` (#162) tells the user: a save's `warning` names a server the profile hands Codex that the `config.toml` of the profile's `CODEX_HOME` (else `~/.codex`) defines with the other transport, and a routed `check_folder` carries `mcpClashes: [{ server, file, openable }]` for the same, only for servers the check's own `mcp` (what the shim adds) lists, plus the checked folder's `.codex/config.toml` files Codex would load (project root, the nearest ancestor with a `.git` holding a `HEAD`, or `project_root_markers` from the user file, down to the folder; only where `[projects."<path>"] trust_level = "trusted"` for the folder, else the root; the git repository root isn't followed, so a worktree trusted only through its main repository is missed). The test is Codex's transport rule on raw keys (`mcp_types.rs:495-550`, so a server import would leave out is seen too), run for any dialect that `McpDialect::merges_same_name` (data only, so `core` and the shim stay free of a parser). The window shows a problem verdict ("codex won't start here", Open `<file>` only where `openable`, i.e. inside home, as `open_in_editor` requires), with a problem slip mark and no first successful check (`checked-once` isn't written), `envrouter check` prints it and exits 1; neither refuses a save, and EnvRouter never edits the agent's file. Codex's MCP OAuth store is left at its default, shared across homes.
- **`npx` servers are rendered with `--prefix=<home>` first** (`mcp::launch_args`). Agents start servers in the project folder, and npm 11 refuses to run (`EBADDEVENGINES`) in a project whose `package.json` pins another package manager under `devEngines`. The prefix moves only where npm looks for a project; the server still runs in the folder. Claude ignores a `cwd` field in a server config (verified), so moving the server isn't an option. `config.json` keeps what the user typed.
- **Secrets live in one item in the platform's store** (`crates/keychain`, `src/store/`): the login Keychain on macOS, the Secret Service (GNOME Keyring, KWallet) on Linux, the Windows Credential Manager on Windows and inside WSL, where the Linux side runs `envrouter-keychain.exe` over interop through its `store-get`/`store-set`/`store-delete` bridge (exit 3 means none; keyed by distro and home, the distro from `WSL_DISTRO_NAME` or, for a process a distro starts without it (a systemd unit, cron, an agent with a bare environment), the note any store use from a WSL terminal leaves in `~/.envrouter/wsl-distro`, written only inside an `~/.envrouter` that exists; with neither, the store says it can't tell which distro this is). A Credential Manager credential holds at most 2,560 bytes, so the item is split across numbered parts. With no store, every call says so; a remote server needing a secret is left out, and a stdio one fails at its start with the launcher's message. The item is keyed by the canonical home folder, so scratch-HOME runs and tests never see the real one. **Where a secret goes.** A stdio server that needs one is rendered as the agent running `~/.envrouter/bin/envrouter-keychain exec <spec>` in its place (`servers/<name>.json` holds a launcher entry: `command` is `paths::keychain_helper(home)`, `args` are `[mcp::LAUNCH_SUBCOMMAND, <spec path>]`, `env` `{}`; Copilot's differs only in `"type": "local"` and `"tools": ["*"]`). `stdio/<name>.json` (0600) is the `mcp::StdioSpec` it reads: the real command, with the `npx --prefix=<home>` rule applied, its args and env with a secret as `{ "secret": "<ID>" }`, never a value, and the `home` the store and the helper belong to, rendered because Copilot passes no `HOME`. Its `launch.json` entry lists no secrets, so for a profile whose secrets are all in stdio servers the shim never runs the helper; a stdio server without a secret keeps its real command, so an exact-command allowlist still matches it. A remote server's headers still refer to `${ENVROUTER_SECRET_<ID>}`, which the shim sets on the agent: those are the secrets that remain in the agent's environment (Claude passes it on to Bash, hooks and command servers without a secret; README's Privacy and security says so). **The window asks whether the store is usable without using it**: `setup_status` carries `secretStoreProblem` (`envrouter_keychain::problem`, each store's `usable`), asked on every focus, so it reads, writes and unlocks nothing and never prompts. macOS and Windows answer `Ok` (nothing can be known without asking the store); the Secret Service opens a plain session and reads the `default` alias; WSL runs the Windows helper with no arguments (usage only). Both run one check at a time on one thread (`envrouter_core::watcher::Watcher`): the first ask waits up to 3 s, a store that hasn't answered by then is _unknown_, not missing (no problem, the lock stays on), and an ask made while a slower check is still running gets the last answer at once, so a hung D-Bus never piles up threads or holds up every refresh. With a problem (`platform.canLock` false) the editor disables the lock and shows values as plain text; `serverOf(draft, canLock)` is the one place that saves a value marked for the store as plain text then (see DESIGN.md "Keychain value"). **The shim never links the Security framework**: loading it cost ~1.4 ms on every launch (measured), so the shim runs the `envrouter-keychain read <ids>` helper, installed beside it, only when `launch.json` lists a secret, which is a remote server's header (`secrets::read_through`, 20 s, shared with the launcher), reads the values from its stdout and sets them on the agent. Keep `crates/core` and `crates/shim` free of any store library; `otool -L` on the release shim lists only `libSystem`, `ldd` only libc and libgcc. The helper's `read [ids]` contract (one JSON line on stdout, non-zero with the reason on stderr) is what the shim and the launcher depend on; keep it. So are `exec <spec>` (`crates/keychain/src/launch.rs`, unix only) and `--launcher-version` (prints `mcp::LAUNCHER_VERSION`, the spec format `exec` reads). `exec` touches no stdin and prints nothing on stdout, so both stay the agent's MCP transport until it execs; it fills in `${NAME}` and `${NAME:-default}` in the spec's plain values (command, args, env, Claude's rules: the agent did this before the launcher started servers in its place) from its own environment, where `ENVROUTER_SECRET_*` never counts; Claude hands it its whole environment, and a launcher entry tells Copilot (`"VAR": "${VAR}"` in its env) and Codex (`env_vars`) which variables to pass on (`StdioSpec::variables`); any failure (the spec gone or unreadable, the read failing or not answering within 20 s, a secret missing, a variable unset with no default) is one `envrouter: …` line on stderr and exit 1 for that one server, no exec (127 and 126 when the command isn't found or can't run). It reads the store through a child `read` of the installed helper with `HOME` set to the spec's `home`, so nothing a store library opens (a Keychain handle, a D-Bus socket) leaks through the `exec` into the server and `HOME` itself never reaches it; strips every inherited `ENVROUTER_SECRET_*`, so a server never sees a remote server's secret; and execs in place, so the PID, process group, cwd, signals and exit status are the server's. A renderer writes specs only for a helper that answers `--launcher-version` with at least its own `LAUNCHER_VERSION`: the app installs both binaries before every render, and see `save_from_cli` below. Secret values are never in EnvRouter's own argv, `config.json` or a rendered file (a secret the user locks into a server's argument is on that server's command line, as before). Typed values travel only with `save_config(payload, secrets)` (the window's Save, or `envrouter secret set <ID>`, which reads the value from stdin or a no-echo prompt), which stores them before writing the config and, once it is written and rendered, drops the secrets nothing names. A secret that a Start Over backup (`config.json.bak`, `.bak-2`, …) still names stays until the backup goes (`config::backed_up_secret_ids`), so putting the backup back brings its servers' secrets with it. The store is read only when a save adds or drops a secret, and one that won't drop a secret gives the save a `warning` (`SaveOutcome::Saved`; the window shows it, the CLI prints it) rather than failing a save whose config is already written; the next save that reaches the store drops it. The window never gets a value back. After installing a new helper while secrets are in use (on save, at launch after an update, or `envrouter install`, which waits for it), the app runs `envrouter-keychain read` once, so macOS asks for access while the app is in front: the helper now reads at every start of a server that needs a secret, several at once, and the grant is asked for once, here. At launch that and a re-render of the MCP files (`commands::render_saved`, which renders config.json as it is under `config.lock`, with the registry's agent rules applied in memory (`agents::with_agents`, never written back, so a rule a release adds, such as Codex's `optionsBeforeSubcommand`, applies from the first launch after an update, #199), and creates nothing without one, so a new helper never meets files that name an old scheme) run on a thread that owns the `Home` lease (`after_install` in `src-tauri/src/lib.rs`), so the uninstall gate waits for it and setup never waits on `config.lock`.
- **Checking a server** (`crates/ops/src/mcp_probe.rs`, on the official `rmcp` crate) runs only when the user clicks: it starts the server with a new terminal's PATH (`shell::login_path`, since an app launched from Finder or a `.desktop` file may have a bare one; kept for 3 minutes per home, and a server check the user clicks takes one no older than 30 s, `login_path_recent`; the npm lookup uses the kept one), lists its tools, and stops it. It opens with `initialize` at 2025-11-25, which every server before MCP 2026-07-28 answers; one that refuses it with a JSON-RPC error, as a server speaking only 2026-07-28 does, is started once more and asked with `server/discover` (10 s), and if that fails too the check reports the first answer. Not rmcp's `Auto` mode: its fixed 10 s probe runs out while a first `npx` run downloads, and the late answer then fails the `initialize` it falls back to. Tool lists from good checks are cached in `~/.envrouter/mcp-tools.json` with the definition they came from, and only offered while it matches. Checks run side by side, so the cache is edited under `mcp-tools.lock`, and a save prunes servers the library dropped. rmcp has no legacy SSE client, so SSE servers report `unsupported`. Tool filtering is a deny list (`disabledTools`), rendered for Claude as `--disallowedTools=mcp__<server>__<tool>`.
- **Import only reads** (`crates/ops/src/mcp_import.rs`): each agent's own MCP files, located by its `mcpFiles` descriptor in `agents.json` (Claude: `.claude.json` in `~` and each profile's config folder, including its `projects` tables, plus `.mcp.json` in trigger folders; Codex: `config.toml` in `~/.codex` and each profile's `CODEX_HOME`, plus `.codex/config.toml` in trigger folders, read as TOML by `toml` (a dependency of `ops` only, never of `core` or the shim) from `[mcp_servers.<name>]` and nothing else in the file; Copilot: `mcp-config.json`, plus `.mcp.json` and `.github/mcp.json` in trigger folders, each with a top-level `mcpServers` or, for the Copilot dialect only and with no `mcpServers` key, as a bare table of named servers, which `read_servers` accepts only when every value has a `command` or `url`, so a `.claude.json` is never mistaken for one; agent files are read as JSONC, as Paste is). `mcpFiles.projectFiles` is a list of paths relative to a trigger folder, subfolders allowed and nothing outside it (it was one `projectFile`, which still reads as a list of one or none, folded into config version 6). Credential-looking env and header values (`SECRET_NAME` in `src/lib/mcp.ts`, or a URL with a password in it) are moved to the secret store on import; `${VAR}` references stay as typed, and so do arguments (a locked argument reaches the server under every agent now, since the launcher fills it in, but it sits on the server's command line; locking credential-looking arguments on import is a follow-up). **What `mcp_import::codex_entry` makes of a Codex server** (checked against 0.164.0's `RawMcpServerConfig`): `command`, `args`, `env`, `url` and `http_headers` as they are, `env_vars` (name or `{ name }`), `env_http_headers` and `bearer_token_env_var` as `${NAME}` references (`Authorization: Bearer ${NAME}`; `isReference` in `src/lib/mcp.ts` counts that as a reference, so the review doesn't lock it into the store), which `mcp.rs` renders back as those fields; a value typed in `env` or `http_headers` wins over a reference to the same name, as it does in Codex. A server with `oauth`, `oauth_resource`, `scopes`, `http_headers_helper`, an `auth` other than `oauth`, `cwd`, an `environment_id` other than `local`, a `remote` `env_vars` source, `bearer_token`, a second `Authorization` header beside `bearer_token_env_var`, or `command` with `url` is left out; tool filters (`enabled_tools`, `disabled_tools`, `tools`), timeouts and `enabled` aren't carried (tools are filtered per profile, and an allow list can't become a deny list without the tool list). A name outside `[A-Za-z0-9_-]{1,64}` stays in the candidate and the review offers `asServerName(name)`, also when it checks "In the library"; EnvRouter never renames a server in Codex's file. **Paste JSON** (`mcp_import::parse_pasted`, the `parse_mcp_json` command) reads the same entries from pasted text, JSONC included, and goes through the same review; text that isn't JSON is read as Codex's TOML (an `mcp_servers` table, a lone server's fields, or a bare table of servers), and an error names the format the text looks like. The catalog (`src/lib/mcpCatalog.ts`) is written from each vendor's README.
- **Pinning an `npx` server** (`src/lib/npm.ts`, `crates/ops/src/npm.rs`): the editor reads the package from the arguments and, on a click (or on opening a catalog pick), asks the user's own npm (`npm view <name> dist-tags --json`, the npm beside the server's `npx`, login PATH, run from home) for its tags, then writes `<name>@<version>` into the argument. Only an exact version counts as pinned. Containers and `uvx` aren't covered yet.
- A profile's servers go to every agent with a descriptor, even if the profile leaves that agent's folder alone, so `config::tool_names` gives those agents shims too.

## How routing resolves (`crates/core/src/resolve.rs`)

- **The most specific profile wins outright.** The deepest trigger containing the folder picks the profile. If that profile doesn't configure the tool, the tool runs with **no** override; it never falls back to a shallower profile. The user chose this deliberately.
- **Compare canonical paths, never `$PWD` text.** `$PWD` keeps typed symlinks and letter case (`~/Dev` on a case-insensitive volume), so both the folder and each trigger go through `fs::canonicalize`.
- **Triggers are whole-subtree prefixes.** `~` is expanded and a trailing `/*` or `/**` is dropped (`config::trigger_base`); any other `*` is rejected. `config.json` keeps what the user typed.
- **A save names its base.** The window passes the config its edit started from; `commands::save` (under `config.lock`, which the CLI's saves take too) refuses it with `changed` and the file as it is now when they differ, before touching the secret store. The window then merges per profile and per server (`src/lib/merge.ts`) and asks (`confirmReplace`) only when both sides changed the same one. The CLI's saves (`commands::save_from_cli`) name the file they read as their base too, and on `changed` read it again and redo their edit (up to three tries), so a window save in between is kept.
- **`config::validate` runs on every save.** It rejects a folder claimed by two profiles, tool or env var names that aren't strict identifiers, and a tool folder that isn't absolute or `~`-based (a relative one would resolve against wherever the tool runs; `resolve` skips one from a hand-edited config too). Tool names become file names in `shims/` and are interpolated into shell probes, so keep `is_command_name` strict.
