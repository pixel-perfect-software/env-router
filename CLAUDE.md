# EnvRouter

@.claude/context/ai-context/docs-overview.md

EnvRouter is a desktop app (Tauri v2) for macOS and Linux, WSL 2 included (native Windows is
planned), that does two things per folder for coding agents
(Claude Code and Copilot CLI): it sets the agent's config variable, so `claude`
run in `~/dev/work` uses a different `CLAUDE_CONFIG_DIR` than in `~/dev/personal`, and it hands
the agent a set of **MCP servers**. The user defines **profiles**: each one maps trigger folders to
a variable per tool and a selection from the MCP **server library**. Profiles are stored in `~/.envrouter/config.json`. A headless CLI, `envrouter`, does the same
setup without the window (servers, WSL distros, scripts).

**Distribution.** There's deliberately no paid Apple Developer ID, so no Developer ID signing or
notarization: the macOS app is signed ad hoc and installed with Homebrew (`brew install --cask
pixel-perfect-software/tap/envrouter`; the cask clears the quarantine flag). Linux gets a `.deb`
and an AppImage from the GitHub release; the CLI installs on both with `brew install
pixel-perfect-software/tap/envrouter-cli`. Pushing a `v*` tag runs `.github/workflows/release.yml`:
macOS and Linux (x86_64, aarch64) builds, one release with `SHA256SUMS`, then
`packaging/homebrew/render.sh` fills the cask and formula templates in `packaging/homebrew/` and
pushes them to the separate `homebrew-tap` repo with the `TAP_TOKEN` secret (a fine-grained
token, Contents read and write on `homebrew-tap` only), so the tap holds only generated files.
EnvRouter is GPL-3.0-or-later; every bundle and CLI archive carries `LICENSE` and
`THIRD-PARTY-NOTICES.txt` (`pnpm notices`, from `packaging/notices/`; CI runs it so a dependency
with no licence text fails there, not at release). Dependencies stay permissive (`deny.toml`).
The tag must equal `version` in `tauri.conf.json` and be on `main`.

**How it works: shims, like mise or volta.** `~/.envrouter/shims/<tool>` is a symlink to
`~/.envrouter/bin/envrouter-shim`, a small Rust binary, and a marked block in the user's shell
startup files puts `shims/` first on PATH. On each run the shim reads `config.json`, picks the
profile for the current folder, sets that tool's variable, adds that profile's MCP servers to
the command line, and `exec`s the real tool found later on PATH. Config edits apply on the next
run in every terminal, with nothing to reload.

**Editor extensions** that run their own copy of an agent (Claude Code for VS Code) bypass PATH,
so they're routed through their process-wrapper setting: the editor runs `envrouter-shim <its
binary> <args>`, and the shim's wrapper mode routes that binary (`crates/shim/src/main.rs`,
`wrapped`). Builds that ship a script instead (Claude Code for VS Code without a native binary,
like 2.1.89's universal build) pass `<interpreter> <script> <args>`, with VS Code's own Electron
helper as Node; the agent is the one whose `ide.extension` names the installed folder
(`<id>-<version>[-<platform>]`) holding the script, and injected arguments go after the script.
`crates/ops/src/editors.rs` sets the setting in VS Code-family user settings (JSONC kept intact,
written through symlinks, never replacing someone else's wrapper) and in remote servers' machine
settings (`~/.vscode-server/data/Machine/settings.json`), which is what
VS Code on Windows reads for a WSL folder. The hook is agent data: `ide` in `src/lib/agents.json`,
saved to `config.agents.*.ide`.

## Where the code lives
- `crates/core`: the config model, routing, MCP rendering, and `platform.rs`, the one place that
  answers what differs between macOS, Linux, WSL and Windows. Callers ask it a question; they
  don't check the OS.
- `crates/ops`: the backend with no UI. `ops::commands` holds the body of every window command;
  `src-tauri/src/lib.rs` wraps each one (adding only the tray and the async runtime), and
  `ops::rpc` serves the same ones by name to `envrouter rpc`, one JSON line each way, the bridge
  a window will use to manage a WSL distro (`wsl.exe -d <distro> -- ~/.envrouter/bin/envrouter
  rpc`). A new command goes in all three; a test pins `rpc::COMMANDS` to the window's handler list (`window_commands!` in `lib.rs`). `open_in_editor` isn't served over rpc.
- `crates/cli` (`envrouter`), `crates/shim`, `crates/keychain` (secrets), and
  `crates/build-support`, which builds the shim and helper for the build scripts that bundle or
  test them.
## How MCP servers reach an agent (`crates/core/src/mcp.rs`)
- **No gateway or daemon.** On every save the app renders, per profile and per agent with an MCP descriptor, one config file per server in the agent's dialect plus a `launch.json` manifest, under `~/.envrouter/mcp/<profile id>/<command>/` (files 0600, folder 0700). The shim reads only the manifest and adds its arguments ahead of the user's own.
- **Always the `--flag=value` form.** Claude's `--mcp-config` and `--disallowedTools` take several values, so `--mcp-config <file>` as two arguments swallows the next one (`claude --mcp-config f mcp --help` breaks; `--mcp-config=f mcp --help` works, verified on 2.1.303). `config::validate` rejects a descriptor without the `=`. `claude mcp list` never shows flag-injected servers. Copilot (verified on 1.0.98) takes `--additional-mcp-config=@<file>` (repeatable, added to the user's own servers) and turns a tool off with one `--deny-tool=<server>(<tool>)` per tool; `copilot mcp list` doesn't show injected servers either. Copilot expands `${VAR}` in env and headers, not args, so a stored secret belongs in an env var or header there.
- **`npx` servers are rendered with `--prefix=<home>` first** (`mcp::launch_args`). Agents start servers in the project folder, and npm 11 refuses to run (`EBADDEVENGINES`) in a project whose `package.json` pins another package manager under `devEngines`. The prefix moves only where npm looks for a project; the server still runs in the folder. Claude ignores a `cwd` field in a server config (verified), so moving the server isn't an option. `config.json` keeps what the user typed.
- **Secrets live in one item in the platform's store** (`crates/keychain`, `src/store/`): the login Keychain on macOS, the Secret Service (GNOME Keyring, KWallet) on Linux, the Windows Credential Manager on Windows and inside WSL, where the Linux side runs `envrouter-keychain.exe` over interop through its `store-get`/`store-set`/`store-delete` bridge (exit 3 means none; keyed by distro and home). A Credential Manager credential holds at most 2,560 bytes, so the item is split across numbered parts. With no store, every call says so and a server needing a secret is left out. The item is keyed by the canonical home folder, so scratch-HOME runs and tests never see the real one. Rendered files refer to `${ENVROUTER_SECRET_<ID>}`. **The shim never links the Security framework**: loading it cost ~1.4 ms on every launch (measured), so the shim runs the `envrouter-keychain read <ids>` helper, installed beside it, only when a server needs a secret (20s timeout), reads the values from its stdout and sets them on the agent. Keep `crates/core` and `crates/shim` free of any store library; `otool -L` on the release shim lists only `libSystem`, `ldd` only libc and libgcc. The helper's `read [ids]` contract (one JSON line on stdout, non-zero with the reason on stderr) is what the shim depends on; keep it. Secret values are never in argv, `config.json` or a rendered file. Typed values travel only with `save_config(payload, secrets)` (the window's Save, or `envrouter secret set <ID>`, which reads the value from stdin or a no-echo prompt), which stores them (and prunes unreferenced ones) before writing the config, and reads the store only when a save adds or drops a secret; the window never gets a value back. After installing a new helper while secrets are in use (on save, or at launch after an update), the app runs `envrouter-keychain read` once, so macOS asks for access while the app is in front.
- **Checking a server** (`crates/ops/src/mcp_probe.rs`, on the official `rmcp` crate) runs only when the user clicks: it starts the server with a new terminal's PATH (`shell::login_path`, since an app launched from Finder or a `.desktop` file may have a bare one), lists its tools, and stops it. Tool lists from good checks are cached in `~/.envrouter/mcp-tools.json` with the definition they came from, and only offered while it matches. rmcp has no legacy SSE client, so SSE servers report `unsupported`. Tool filtering is a deny list (`disabledTools`), rendered for Claude as `--disallowedTools=mcp__<server>__<tool>`.
- **Import only reads** (`crates/ops/src/mcp_import.rs`): each agent's own MCP files, located by its `mcpFiles` descriptor in `agents.json` (Claude: `.claude.json` in `~` and each profile's config folder, including its `projects` tables, plus `.mcp.json` in trigger folders). Credential-looking env and header values (`SECRET_NAME` in `src/lib/mcp.ts`, or a URL with a password in it) are moved to the secret store on import; `${VAR}` references stay as typed, and so do arguments, since Copilot doesn't expand a secret there. **Paste JSON** (`mcp_import::parse_pasted`, the `parse_mcp_json` command) reads the same entries from pasted text, JSONC included, and goes through the same review. The catalog (`src/lib/mcpCatalog.ts`) is written from each vendor's README.
- A profile's servers go to every agent with a descriptor, even if the profile leaves that agent's folder alone, so `config::tool_names` gives those agents shims too.

The window has two views, switched in the titlebar (⌘1, ⌘2; Ctrl off macOS). **Profiles** is built around a
direction called **the Sorting Frame**: one card per profile with its folders filed inside,
rendered as modern layered Mac cards (the user asked for clearly separated surfaces, so don't
regress to flat ruled grids), with a profile's editor as a right-side inspector. **MCP Servers** is
a list beside the server editor, with Catalog and Import in the same detail area. Assigning a
server to a profile works from both sides (the profile's MCP checklist, the server's Used by
toggles), so keep both. Before changing the UI, read `PRODUCT.md`,
`.impeccable/surfaces/src-app-tsx.md` (the direction contracts) and `DESIGN.md` (tokens and
rules: one accent button per state, status-free profile colours). The window is translucent
over macOS under-window vibrancy (`transparent`, `windowEffects` and `macOSPrivateApi` in
`tauri.conf.json`, and the `macos-private-api` Tauri feature): only the ground lets it through,
cards stay opaque, and the browser mock shows the solid ground. The app also lives in the menu
bar (`src-tauri/src/tray.rs`), whose menu refreshes when the window gains focus and when the pointer reaches the icon (macOS, Windows), so a CLI change or hand edit shows; on macOS closing the window only hides it.

**Off macOS the window follows the system** (`src-tauri/tauri.linux.conf.json`, DESIGN.md
"Platform chrome"): native decorations, an opaque window, no traffic-light inset, Ctrl
shortcuts, the store called "keyring" ("Credential Manager" inside WSL), and closing quits, since GNOME has no tray to come back
from. The frontend reads the platform from `SetupStatus.platform` through `usePlatform()`
(`src/lib/platform.ts`); add a platform difference there, not with an inline check. On Linux
the app's binary is `envrouter-app`, so `envrouter` is always the CLI.

## How routing resolves (`crates/core/src/resolve.rs`)
- **The most specific profile wins outright.** The deepest trigger containing the folder picks the profile. If that profile doesn't configure the tool, the tool runs with **no** override; it never falls back to a shallower profile. The user chose this deliberately.
- **Compare canonical paths, never `$PWD` text.** `$PWD` keeps typed symlinks and letter case (`~/Dev` on a case-insensitive volume), so both the folder and each trigger go through `fs::canonicalize`.
- **Triggers are whole-subtree prefixes.** `~` is expanded and a trailing `/*` or `/**` is dropped (`config::trigger_base`); any other `*` is rejected. `config.json` keeps what the user typed.
- **`config::validate` runs on every save.** It rejects a folder claimed by two profiles, tool or env var names that aren't strict identifiers, and a tool folder that isn't absolute or `~`-based (a relative one would resolve against wherever the tool runs; `resolve` skips one from a hand-edited config too). Tool names become file names in `shims/` and are interpolated into shell probes, so keep `is_command_name` strict.

## The shim must never block the tool
A missing config means the tool runs silently. A broken one prints a warning and the tool still runs. The same goes for MCP: no manifest means no injection, a broken one warns, a server whose secret can't be read is left out with a warning, `--strict-mcp-config` (or `ENVROUTER_MCP=0`) turns injection off for that run, and so does a first argument in the agent's `skipSubcommands` (Claude's `plugin`: `claude plugin test` refuses any option before `plugin`, verified on 2.1.306), and explaining never asks the secret store. When looking for the real binary, the shim skips the shims directory, empty PATH entries (the current directory), and anything that canonicalizes to itself, so it can never exec itself in a loop. In wrapper mode (run under its own name, for an editor) it wraps only an absolute path to an executable that isn't a shim; one it can't name as a tool (not named like a command, and not running a script from an agent's extension) runs unrouted with a warning rather than not at all. Keep these properties; `crates/shim/tests/shim.rs` covers each one.

## Constraints
- **No logins or OAuth.** EnvRouter never signs anyone into an agent or an MCP server; agents run their own sign-in (`/mcp`). The one credential it handles is MCP secret values the user enters, kept in the secret store item above.
- **Tauri v2 APIs only.** v1 examples (`tauri.conf.json > allowlist`, `@tauri-apps/api/fs`) are wrong here. Use plugins and `capabilities/*.json`.
- **All file access happens in Rust commands.** There's deliberately no fs plugin, and `capabilities/default.json` grants only the three plugin calls the window makes (dialog open, dialog message, opener reveal), one by one. Don't go back to a plugin's `:default` set, and don't add `@tauri-apps/plugin-fs` back.
- **The window has a CSP** (`app.security.csp` in `tauri.conf.json`): scripts and styles from the bundle only, and IPC. Loading anything remote or adding an inline script means changing the policy on purpose.
- **Keep the data model tool-agnostic.** `Profile.tools` is a `Record<toolName, { envVar, path }>`. Nothing in Rust branches on an agent's name: agent behaviour is data in `src/lib/agents.json` (its variable, and an MCP descriptor naming a config *dialect*, a file format), which the window (`withAgents` in `tools.ts`) rewrites into `config.agents` on every save. The CLI (`envrouter_core::agents::with_agents`) only fills in agents the config doesn't name yet, saved by `apply` and used in memory by `install` and `editor`, so a CLI-only machine needs no window and a CLI a release apart never undoes the app's descriptors. CLI saves go through `save_config_from_cli`, which installs its own shim and helper only where none is installed. Rust renders dialects, not agents. Add an agent with one entry in `src/lib/agents.json`, and only after checking its docs: the variable must relocate logins too, not just settings; note quirks in the entry's `note`, and why-comments beside the import in `tools.ts`, since JSON can't hold them. A config that still names an agent the window no longer offers keeps loading, saving and routing. `save_config` creates missing agent folders inside home. Codex and Gemini CLI were dropped to keep the app focused; they're future add-ons (Codex: `-c mcp_servers.*` overrides with secrets through `env_vars`, and its MCP OAuth tokens are shared across `CODEX_HOME`s; Gemini: settings in a file named by `GEMINI_CLI_SYSTEM_DEFAULTS_PATH`, which shallow-merges `mcpServers`, and `GEMINI_CLI_HOME` holds a `.gemini` folder).
- **Bump `CONFIG_VERSION` in `config.rs`** for any change to the shape of `config.json`, and migrate older versions in `config::load`. The shim refuses configs from a newer version.

## Conventions
- **pnpm only, versions in `.tool-versions`** (asdf): Node 24.21.0 and pnpm 12.14.0. `packageManager` in `package.json` repeats the pnpm version for `pnpm/action-setup` and pnpm's own version switching, so bump both together; the workflows read Node from `.tool-versions` (`node-version-file`).
- **Biome, not ESLint or Prettier:** 2-space indentation, **single quotes, no semicolons**, 150-column lines. Don't copy the double-quote/semicolon style from Tauri docs. Run `pnpm format-and-lint:fix`.
- **Tailwind v4** through `@tailwindcss/vite`: no config file and no PostCSS; theme tokens go in `src/index.css` with `@theme`.
- **Rust is a Cargo workspace** rooted at the repo (`crates/{build-support,cli,core,keychain,ops,shim}`, `src-tauri`), with one `target/` at the root. Use `cargo fmt --all`. Release profile settings live in the root `Cargo.toml`.
- **Workflows pin every action to a release's full commit SHA**, with the version in a comment (`uses: actions/checkout@<sha> # v7.0.1`), and pin the tools they install (`cargo-deny@…`, Node from `.tool-versions`); `.github/dependabot.yml` proposes updates monthly. Checkouts set `persist-credentials: false` unless they push (only the release's tap checkout does), and the release workflow restores no caches, so what users install is built only from the tagged source. CI's `changes` job skips the other jobs for docs-only changes rather than `paths-ignore`, because branch protection requires the `linux` and `macos` checks and a skipped job counts as passing. For the same reason `linux` is a gate over the parallel `checks` (frontend, licences, notices) and `rust` jobs that runs with `if: always()` and checks their results: a gate skipped by a failure would let the merge through. The release builds each platform's app and CLI in parallel jobs, renders the notices inside each while it compiles (`tauri build --no-bundle`, then `tauri bundle` with the licences as resources), and restores no caches.
- **Rust tooling:** `rust-toolchain.toml` pins 1.99.0 (rustup reads it; Homebrew Rust doesn't, so match it by hand). `[workspace.lints]` denies `unsafe` (denied, not forbidden, so the one FFI module, `crates/keychain/src/store/windows.rs`, can allow it, arguing each call's safety) and adds a curated slice of clippy pedantic; every member opts in with `[lints] workspace = true`. `cargo deny check` (`deny.toml`) allows permissive licences only, so no GPL code can arrive through a dependency, and checks RustSec advisories. `cargo machete` finds unused dependencies. CI runs all of them.

## Gotchas
- **Tests must never touch the real home directory.** Shell code resolves startup files from the `home` it's given, and finds zsh's `ZDOTDIR` by asking a fresh zsh, never from the process environment. Don't read `ZDOTDIR` or `HOME` from `std::env` in testable code. Claude Code's own environment sets `ZDOTDIR`.
- **The shell block is POSIX sh** (`shell.rs`, `POSIX_BODY`), so it's safe when bash's login file is `.profile`. bash's files depend on the terminal (`bash_startup_files`): on a Linux desktop only `.bashrc`; where terminals start login shells (macOS, WSL), the first existing login file, and with none of them `.bash_profile` on macOS but `.profile` on Linux. Never create a `.bash_profile` on Linux: it hides the `.profile` distros source `.bashrc` from. It moves the shims directory to the front of PATH rather than skipping it when it's already there, because nested shells re-prepend `~/.local/bin`.
- **`check_folder` emulates a new terminal window** of the platform (`crates/core/src/platform.rs`): a cleared environment with the PATH that platform's terminals start with (`new_terminal_path`: macOS's bare one, `/etc/environment` on Linux, WSL's default plus its Windows folders) and the session's variables, and an interactive shell that's a login shell on macOS and WSL but not on a Linux desktop. The login shell comes from `$SHELL`, or `getent passwd` when an app started from a `.desktop` file has none. `-c` never draws a prompt, so the probe runs the prompt hooks once itself (zsh `chpwd`/`precmd`, bash `PROMPT_COMMAND`, fish `fish_prompt` events): mise and direnv reorder PATH there. When the shim was first before the hooks and isn't after, the result says `byPromptHook`. Output goes to temp files, not pipes, because prompt themes leave background jobs holding pipes open, and markers are matched anywhere in a line, because hooks and startup files print without newlines. It never runs the real tool. The shim's `ENVROUTER_EXPLAIN=1` mode reports the route instead.
- **The shim and the secrets helper are built by `crates/build-support`**, called from `src-tauri/build.rs` (and `crates/ops/build.rs`, whose tests install them), into `target/shim/` (inside `CARGO_TARGET_DIR` when set); the app's build stages them as `src-tauri/binaries/envrouter-{shim,keychain}-<triple>` for `bundle.externalBin`; the app installs both into `~/.envrouter/bin/` through a temp file and a rename (overwriting a signed binary in place gets it SIGKILLed). It's always built with the `helpers` profile (release with whole-program LTO and one codegen unit, kept for the binaries on every agent launch; `release` itself has neither and optimises for size, which builds the app and CLI twice as fast and downloads smaller), whatever the outer profile: every profile stages to that one file, so per-profile builds let `tauri build` bundle a debug shim. The macOS bundle is arm64-only for now; Intel support needs a universal build plus `lipo` of the shim. Linux builds also ship `envrouter-keychain.exe` (cross-compiled with mingw) beside the shim, and `shims::install_bundled` installs it when it's there, for WSL. `shims::bundled` follows links, so a CLI linked into Homebrew's `bin` finds the helpers in its keg.
- **Icons are drawn as SVG** in `src-tauri/icons/`: `app-icon.svg` (128 px and up), `app-icon-small.svg` (a bolder cut for 64 px and under) and `tray.svg` (the menu bar template). Every PNG and `icon.icns` is rendered from them at its exact pixel size with a transparent background, the `.icns` through an `iconutil` iconset that takes the small cut for 16 to 64 px. Don't run `tauri icon`: it rebuilds every size from one source, losing the small cut, and recreates the Windows tiles. The tray image is a template, so macOS reads only its alpha; its cutouts must be mask transparency, not white fills. tray-icon draws it 18 pt tall whatever its size, so `tray.svg`'s viewBox hugs the glyph and `tray.png` is 36 px. Rendered PNGs carry their origin (`impeccable embed-prompt --read`).
- **Signing is ad hoc** (`bundle.macOS.signingIdentity: "-"`), so the bundle has a valid signature for the Mac that built it, and the hardened runtime is off. Turning it on would make dyld strip every `DYLD_*` variable from the shim's environment before it execs the real tool (verified). If it's ever needed, sign with an entitlements file containing `com.apple.security.cs.allow-dyld-environment-variables`; Tauri applies one file to the app and the shim alike.
- **Review the UI in a browser, never against the real home folder.** `pnpm dev` and then `http://localhost:1420/?scenario=first-run|populated|mcp|shadowed|broken` (add `&platform=linux` or `&platform=wsl` for those systems, and `&check=`, `&shim=stale` or `&store=off` for states a real machine can be in; docs/contributing.md lists them) runs the frontend with every Tauri call answered by `src/dev/mockTauri.ts` (dev-only; `window.__mockDrop(path, x, y)` simulates a Finder drop). Keep the mock answering as the real backend does, with fresh objects each call: a check in a shell that's off returns `shadowedOnPath`, not `notFound`, whenever the tool is installed. `src/dev/mockTauri.test.ts` pins the mock's answers that mirror backend messages. Running the real app touches `~/.envrouter`, and its shell toggles edit the real startup files. To try the real app safely, launch the built binary with `HOME` set to a scratch folder.
- **Wire types live in `src/lib/types.ts`.** Rust tests pin the JSON (`wire_format_matches_the_typescript_types` in `shell.rs` and `editors.rs`; the rpc envelope in `rpc.rs`), so change both sides together.
- **Check Linux and Windows from a Mac with `dev/containers/compose.yaml`** (Podman or Docker, project `envrouter-dev`): `linux-test` (backend tests with every shell required, and a GNOME Keyring round trip), `linux-app`, `linux-bundle` (the `.deb` and AppImage as the release builds them), `windows-helper-build` then `windows-helper-wine` (the Credential Manager round trip under Wine, a test-only Windows compatibility layer; only Wine runs emulated, since qemu crashes Rust tooling). The shell tests skip a missing shell, except under `ENVROUTER_REQUIRE_SHELLS=1`, which CI and the containers set.
- **`XDG_CONFIG_HOME` counts only inside the given home** (`platform::xdg_config_home`), so a test's scratch home can't reach the real config folder.
- `.claude/settings.json` denies Claude read access to `.env` files. Ask the user for variable names instead.
