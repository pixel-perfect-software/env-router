# EnvRouter

@.claude/context/ai-context/docs-overview.md

EnvRouter is a desktop app (Tauri v2) for macOS and Linux, WSL 2 included (native Windows is
planned), that does two things per folder for coding agents
(Claude Code, Copilot CLI and Codex CLI): it sets the agent's config variable, so `claude`
run in `~/dev/work` uses a different `CLAUDE_CONFIG_DIR` than in `~/dev/personal`, and it hands
the agent a set of **MCP servers**. The user defines **profiles**: each one maps trigger folders to
a variable per tool and a selection from the MCP **server library**. Profiles are stored in `~/.envrouter/config.json`. A headless CLI, `envrouter`, does the same
setup without the window (servers, WSL distros, scripts).

**Distribution.** There's deliberately no paid Apple Developer ID, so no Developer ID signing or
notarization: the macOS app is signed ad hoc and installed with Homebrew (`brew install --cask
pixel-perfect-software/tap/envrouter`; the cask clears the quarantine flag). Linux gets a `.deb`
and an AppImage from the GitHub release; the CLI installs on both with `brew install
pixel-perfect-software/tap/envrouter-cli`. Pushing a `v*` tag runs `.github/workflows/release.yml`:
macOS and Linux (x86_64, aarch64) builds, one release with `SHA256SUMS`, then
`packaging/homebrew/render.sh` fills the cask and formula templates in `packaging/homebrew/` and
pushes them to the separate `homebrew-tap` repo with the `TAP_TOKEN` secret (a fine-grained
token, Contents read and write on `homebrew-tap` only), so the tap holds only generated files.
EnvRouter is GPL-3.0-or-later; every bundle and CLI archive carries `LICENSE` and
`THIRD-PARTY-NOTICES.txt` (`pnpm notices`, from `packaging/notices/`; CI runs it so a dependency
with no licence text fails there, not at release). Dependencies stay permissive (`deny.toml`).
The version, the tag and the release flow are under **Git workflow** below.

**How it works: shims, like mise or volta.** `~/.envrouter/shims/<tool>` is a symlink to
`~/.envrouter/bin/envrouter-shim`, a small Rust binary, and a marked block in the user's shell
startup files puts `shims/` first on PATH. On each run the shim reads `config.json`, picks the
profile for the current folder, sets that tool's variable, adds that profile's MCP servers to
the command line, and `exec`s the real tool found later on PATH. Config edits apply on the next
run in every terminal, with nothing to reload.

**Editor extensions** that run their own copy of an agent (Claude Code for VS Code) bypass PATH,
so they're routed through their process-wrapper setting: the editor runs `envrouter-shim <its
binary> <args>`, and the shim's wrapper mode routes that binary (`crates/shim/src/main.rs`,
`wrapped`). Builds that ship a script instead (Claude Code for VS Code without a native binary,
like 2.1.89's universal build) pass `<interpreter> <script> <args>`, with VS Code's own Electron
helper as Node; the agent is the one whose `ide.extension` names the installed folder
(`<id>-<version>[-<platform>]`) holding the script, and injected arguments go after the script.
`crates/ops/src/editors.rs` sets the setting in VS Code-family user settings (JSONC kept intact,
written through symlinks, never replacing someone else's wrapper) and in remote servers' machine
settings (`~/.vscode-server/data/Machine/settings.json`), which is what
VS Code on Windows reads for a WSL folder. The hook is agent data: `ide` in `src/lib/agents.json`,
saved to `config.agents.*.ide`.

## Where the code lives

- `crates/core`: the config model, routing, MCP rendering, and `platform.rs`, the one place that
  answers what differs between macOS, Linux, WSL and Windows. Callers ask it a question; they
  don't check the OS.
- `crates/ops`: the backend with no UI. `ops::commands` holds the body of every window command;
  `src-tauri/src/lib.rs` wraps each one (adding only the tray and the async runtime), and
  `ops::rpc` serves the same ones by name to `envrouter rpc`, one JSON line each way, the bridge
  a window will use to manage a WSL distro (`wsl.exe -d <distro> -- ~/.envrouter/bin/envrouter
  rpc`). See `crates/ops/CLAUDE.md` for how a new command is added.
- `crates/cli` (`envrouter`), `crates/shim`, `crates/keychain` (secrets), and
  `crates/build-support`, which builds the shim and helper for the build scripts that bundle or
  test them.
- **`uninstall`**: see `crates/ops/CLAUDE.md`.

## How MCP servers reach an agent (`crates/core/src/mcp.rs`)

See `crates/core/CLAUDE.md`: no gateway or daemon, the `--flag=value` form, secrets in the platform store, checking, import and pinning a server.

The window has two views, switched in the titlebar (⌘1, ⌘2; Ctrl off macOS). **Profiles** is built around a
direction called **the Sorting Frame**: one card per profile with its folders filed inside,
rendered as modern layered Mac cards (the user asked for clearly separated surfaces, so don't
regress to flat ruled grids), with a profile's editor as a right-side inspector. **MCP Servers** is
a list beside the server editor, with Catalog and Import in the same detail area. Assigning a
server to a profile works from both sides (the profile's MCP checklist, the server's Used by
toggles), so keep both. Before changing the UI, read `PRODUCT.md`,
`.impeccable/surfaces/src-app-tsx.md` (the direction contracts) and `DESIGN.md` (tokens and
rules: one accent button per state, status-free profile colours). The window is translucent
over macOS under-window vibrancy (`transparent` and `windowEffects` in `tauri.conf.json`; the
private API a transparent window needs has been always on since Tauri 2.12.1, so there's no
`macOSPrivateApi` or `macos-private-api` feature): only the ground lets it through,
cards stay opaque, and the browser mock shows the solid ground. The app also lives in the menu
bar (`src-tauri/src/tray.rs`), whose menu refreshes when the window gains focus and when the pointer reaches the icon (macOS, Windows), so a CLI change or hand edit shows; on macOS closing the window only hides it. The menu also holds **Check Last Folder** and a disabled version line (`EnvRouter 0.11.0`, from the package version). "Last" is the folder of the window's latest `check_folder`, kept in `~/.envrouter/last-folder.json` (`ops::last_folder`): the window's `localStorage` isn't readable from Rust, and the file goes with `~/.envrouter` on uninstall. The item is disabled while there is none or the folder has gone, and chooses by leaving a `MenuRequest` for the window (the same way "Check Folder…" does): the request waits in the backend (`tray::MENU_REQUEST`) and the window takes it (`take_menu_request`) when it hears `menu-request` and once as it starts listening, since an event sent before the webview listens (the first show after a hidden launch, a reload) is lost; it waits for config.json to be read, then checks the folder as a drop does, or says why it can't (the profile editor is open, config.json can't be read). **The window comes back where it was** (`tauri-plugin-window-state`, with `SIZE | POSITION | MAXIMIZED` only: not `VISIBLE`, or a window hidden to the menu bar when the app quit would never open again, and not `DECORATIONS`, which the platform config owns). The plugin saves at exit, and EnvRouter saves again when the macOS close hides the window, so a crash or force quit loses little. Its file, `.window-state.json`, is in the app's config folder (see the uninstall bullet), not in `~/.envrouter`, and that folder is in `platform::app_data_dirs`, so both the CLI's uninstall and the app's exit-time `remove_app_data` delete it (the plugin saves on `RunEvent::Exit` before the app's own callback, which deletes it after). **The bundle identifier is `ca.pixel-perfect.envrouter`; the one before it (`platform::LEGACY_APP_IDENTIFIERS`, the only place the old name is written in code, besides the cask) is cleaned up at launch** by `leave_legacy_identifier` in `src-tauri/src/lib.rs`, a plugin added before window-state so it sets up first (plugins start in order). It copies the old `.window-state.json` into the new config folder when the new has none (`ops::legacy_identifier::carry_window_state`, synchronous, since window-state reads its file while it starts, and read-only on the old side). Then a thread runs `clean_up_old_identifier`, which keeps `.legacy-cleaned` in the new config folder (`done`, or the number of launches that left something, three at most): with no legacy folder on disk it just notes `done` (a fresh install asks nothing of the system); while another process of this user (`platform::user_processes`: `/proc` owned by the uid on Linux, `ps -U <uid> -x` on macOS) runs the app's binary (`platform::is_app_binary`; 0.7.2 and before don't hold `app.lock`, and an AppImage, `.deb` or copied app isn't quit by the cask) it does nothing and notes nothing, so a later launch retries (a process list it can't get is logged and counts as not running); otherwise it deletes the legacy identifier's webview data, caches, saved state, preferences and config folder (`uninstall::remove_legacy_with`, over `AppData::legacy`) and runs `defaults delete` for the old domain, and notes `done` only if nothing was left. What it leaves (an undeletable folder, one under an `XDG_*` outside home, a deleted link's target) goes to stderr and counts a try; the uninstall names the leftovers again. The webview's storage can't move (WKWebView and WebKitGTK key it by identifier), so the last view resets once. First-run's last step used to live in that storage too (`envrouter.checkedOnce`); it is now the backend's: `commands::check_folder` writes `~/.envrouter/checked-once` (`ops::checked_once`) the first time a check comes back routed, `SetupStatus.checkedBefore` reports it, and `healthOf` counts it. For an install set up under the old identifier, `legacy_identifier::carry_checked_once` writes it in the plugin's setup (file reads only, so before the window's first status) when an old folder exists, `config.json` has a profile and a startup file holds the shell block: it was plainly set up, which is all the old answer meant. Nothing else is derived from the identifier here: the Linux `.desktop` file, its `StartupWMClass` and the AppImage take `mainBinaryName` and `productName`, GTK's app id is off (`enable_gtk_app_id`), and the tray id is its own constant. The Keychain secrets item is keyed by service and home, and the helper's access is granted to its ad hoc `cdhash` (its code-signing identifier is `envrouter-keychain-<hash>`, not the bundle id), so a new identifier neither moves nor re-prompts it beyond what any update that changes the helper does (`ask_keychain_access`). The window never calls the plugin's commands, so `capabilities/default.json` grants none of its permissions. The last view (Profiles or MCP Servers) is `localStorage` (`src/lib/lastView.ts`). **Quitting with unsaved edits asks first** (`src-tauri/src/quit.rs`): the editors report their dirty state (`src/lib/unsaved.ts` → `set_unsaved_edits`), and the menu bar's Quit, ⌘Q and closing the window off macOS come through `ExitRequested` or `CloseRequested`, which ask the window (`quit-requested`) only while it holds edits; a second quit it hasn't answered goes ahead. macOS's predefined Quit can't be asked (tao handles only `applicationWillTerminate`), so the app menu's Quit is EnvRouter's own item (`menu::app_menu`); the Dock's Quit still terminates. That menu also holds Settings… (⌘,) after About and the Help menu's links (`src-tauri/src/menu.rs`, `help.rs`): there's no Preferences window (PRODUCT.md, principle 1), so Settings… and ⌘, (Ctrl+, off macOS, where there's no menu bar) open the Shells popover, from any view, but not with the profile inspector open, while an uninstall runs, or with no shell to show (the control they stand for is absent); the Shells popover also carries the Documentation and Report an Issue links, which is where Linux and WSL reach them. A server editor holding edits isn't remounted by a reload that changed its server; it says so instead.

**Off macOS the window follows the system** (`src-tauri/tauri.linux.conf.json`, DESIGN.md
"Platform chrome"): native decorations, an opaque window, no traffic-light inset, Ctrl
shortcuts, the store called "keyring" ("Credential Manager" inside WSL), and closing quits, since GNOME has no tray to come back
from. The frontend reads the platform from `SetupStatus.platform` through `usePlatform()`
(`src/lib/platform.ts`); add a platform difference there, not with an inline check. Wording and
paths come from the backend rather than the window: `SetupStatus` carries the store's name, the file manager and its
reveal verb (`Platform::file_manager`, `reveal_verb`, which also word the menu bar) and `shimPath`, a `ConfigFault`
carries the unreadable file's `path`, and each `EditorStatus` its `label`. Only what must be right at the first paint,
before the status arrives, is guessed from the user agent (`ownsTitlebar`, `vibrant`), with defaults for the words that
the backend's replace, kept in `src/lib/platformWords.json` (the browser mock answers from it too; a test in `platform.rs` holds
it to what `Platform` says, so change both together). A failed `get_config` names the file in `ConfigFault.path`, and over
`envrouter rpc` in `errorPath`. Nothing builds a `~/.envrouter` path or keeps a copy of the editor list. On Linux
the app's binary is `envrouter-app`, so `envrouter` is always the CLI.

## The shim must never block the tool

It also must stay cheap: it runs before every agent launch. CI's `shim-timing` job fails when, with 60 triggers and 8 PATH entries ahead of the tool, its median launch takes over 1.8x a bare exec's (`.github/scripts/shim-overhead.sh`; a ratio because runner machines differ in speed, on Linux because macOS runners' timings swing 16x). Match triggers and PATH entries by one `stat` each, not `canonicalize`, which walks every component.

A missing config means the tool runs silently. A broken one prints a warning and the tool still runs. The same goes for MCP: no manifest means no injection, a broken one warns, a remote server whose secret can't be read is left out with a warning (a stdio server that needs one is the launcher's to fail at its start, for that server alone, never the shim's), `--strict-mcp-config` (or `ENVROUTER_MCP=0`) turns injection off for that run, and so does the agent's subcommand when it's in `skipSubcommands`: its first argument, or, for an agent whose `optionsBeforeSubcommand` is set (Codex), the first word past its options and their values (one pass over argv, no allocation; a `--` or a prompt ahead means none) (Claude's background-session commands, `daemon` among them, read as a prompt with an option ahead of them, `remote-control` and its alias `rc` refuse one, its hidden aliases `remote`, `sync` and `bridge` read as a prompt too, and `claude plugin test` refuses any option before `plugin`, which is why Claude's is null; swept on 2.1.309, the aliases on 2.1.310, the list and reasons beside the import in `tools.ts`), and so does an existing file in its `skipIfPresent` (Claude's enterprise `managed-mcp.json`: Claude Code exits at startup when it's given servers on a managed machine), with one warning, which explain mode and `check_folder` report as `mcpManagedBy`. Explaining never asks the secret store. A routed folder inside home that's gone is made again just before the exec, since Codex exits without it (explain mode makes nothing). When looking for the real binary, the shim skips the shims directory, empty PATH entries (the current directory), and anything that canonicalizes to itself, so it can never exec itself in a loop. A wrapper further along PATH that looks there for the tool, skipping only itself (VS Code's `copilot-shim`), would bring it back: the shim leaves its process and parent IDs in `ENVROUTER_SHIM_RAN`, which exec keeps, and, run again in that same process, runs the same program once more with nothing added and every folder holding a shim for the tool taken off PATH (`programs::without_shims`), so the wrapper finds the tool itself or gives its own answer. In wrapper mode (run under its own name, for an editor) it wraps only an absolute path to an executable that isn't a shim; one it can't name as a tool (not named like a command, and not running a script from an agent's extension) runs unrouted with a warning rather than not at all. Keep these properties; `crates/shim/tests/shim.rs` covers each one, and `mcp.rs`'s tests the search for a subcommand past options.

## Constraints

- **No logins or OAuth.** EnvRouter never signs anyone into an agent or an MCP server; agents run their own sign-in (`/mcp`). The one credential it handles is MCP secret values the user enters, kept in the secret store item above.
- **Tauri v2 APIs only.** v1 examples (`tauri.conf.json > allowlist`, `@tauri-apps/api/fs`) are wrong here. Use plugins and `capabilities/*.json`.
- **All file access happens in Rust commands.** There's deliberately no fs plugin, and `capabilities/default.json` grants only the two plugin calls the window makes (dialog open, dialog message), one by one; links open from Rust (`help::open`), never through the plugin's `allow-open-url`. Don't go back to a plugin's `:default` set, and don't add `@tauri-apps/plugin-fs` back. `build.removeUnusedCommands` (`tauri.conf.json`) compiles out every plugin command no capability grants: the fs plugin, which the dialog plugin depends on, keeps none, and dialog keeps only the two, and the opener, registered for its Rust API, keeps none. So a new plugin call needs its permission here, or it isn't in the build at all (the app's own commands are never removed: there's no app ACL).
- **The window has a CSP** (`app.security.csp` in `tauri.conf.json`): scripts and styles from the bundle only, and IPC. Loading anything remote or adding an inline script means changing the policy on purpose.
- **Keep the data model tool-agnostic.** `Profile.tools` is a `Record<toolName, { envVar, path }>`. Nothing in Rust branches on an agent's name: agent behaviour is data in `src/lib/agents.json` (its variable, and an MCP descriptor naming a config _dialect_, a file format), which the window (`withAgents` in `tools.ts`) rewrites into `config.agents` on every save. The CLI (`envrouter_core::agents::with_agents`) only fills in agents the config doesn't name yet (and adds the registry's skip rules, `skipAnyArgs`, `skipSubcommands` and `skipIfPresent`, to agents it does name, and the options an agent reads ahead of a subcommand (`optionsBeforeSubcommand`, version 7: a null one becomes the registry's, its lists merged like the skip rules; a registry null, Claude's and Copilot's, changes nothing): each only turns injection off for a run it would break, and a rule a release adds wouldn't reach a machine with no window otherwise; and, in a config from before version 6, gives one named with no `mcp` the registry's, since 0.9 saved Codex that way; a version 6 config keeps what it says, so a later release that drops a descriptor isn't undone), saved by `apply` and used in memory by `install`, `editor` and `render_saved`, so a CLI-only machine needs no window and a CLI a release apart never undoes the app's descriptors. CLI saves go through `save_from_cli`, which installs its own shim and helper only where the installed shim can't read the config version it writes (none, one that answers `envrouter-shim --config-version` with an older version, or one from 0.7.0 or earlier, which doesn't answer: after `brew upgrade envrouter-cli` the old shim stays in `~/.envrouter/bin`) or the installed helper can't start the specs it renders (none, or one that doesn't answer `envrouter-keychain --launcher-version` with at least `LAUNCHER_VERSION`; 0.8.0's prints its usage and exits 2). What stays unsolved is only that a 0.8 app started after a newer CLI puts its own helper back without rendering, so servers that need a secret fail with the helper's usage line until an app save or `envrouter apply`; an older CLI saving over a new render writes the old scheme, which the new shim and helper still run. `envrouter install` renders again only when it changed an installed file. Rust renders dialects, not agents. Add an agent with one entry in `src/lib/agents.json` (its `mark` slug names the logo `AgentMark` draws; none, or one `icons.tsx` doesn't know, gets a generic bot), and only after checking its docs: the variable must relocate logins too, not just settings; note quirks in the entry's `note`, and why-comments beside the import in `tools.ts`, since JSON can't hold them. A config that still names an agent the window no longer offers keeps loading, saving and routing. `save_config` creates missing agent folders inside home. Codex CLI routes by `CODEX_HOME` and takes servers through the `codex` dialect (above), and imports from its TOML (`mcpFiles`, above); its MCP OAuth tokens are shared across `CODEX_HOME`s (M4, `docs/roadmap.md`). Gemini CLI was dropped to keep the app focused and is a future add-on (settings in a file named by `GEMINI_CLI_SYSTEM_DEFAULTS_PATH`, which shallow-merges `mcpServers`, and `GEMINI_CLI_HOME` holds a `.gemini` folder).
- **Bump `CONFIG_VERSION` in `config.rs`** for any change to the shape of `config.json`, and migrate older versions in `config::load`. The shim refuses configs from a newer version. Version 6 added the `codex` dialect, which an older `McpDialect` can't parse: a 0.9.0 shim given the file warns "unknown variant `codex`" and runs every agent unrouted (the parse fails before the version check), so a CLI save installs a shim that reads it. Version 7 added `optionsBeforeSubcommand`, a key an older CLI would drop on its next save (serde ignores what it doesn't know) and so bring #187 back, so a 0.10 CLI refuses the file instead ("…is from a newer version of EnvRouter. Update EnvRouter to use it.").

## Conventions

- **pnpm only, versions in `.tool-versions`** (asdf): the Node and pnpm versions are in `.tool-versions`. `packageManager` in `package.json` repeats the pnpm version for `pnpm/action-setup` and pnpm's own version switching, so bump both together; the workflows read Node from `.tool-versions` (`node-version-file`).
- **Biome, not ESLint or Prettier:** 2-space indentation, **single quotes, no semicolons**, 150-column lines. Don't copy the double-quote/semicolon style from Tauri docs. Run `pnpm format-and-lint:fix`.
- **Tailwind v4** through `@tailwindcss/vite`: no config file and no PostCSS; theme tokens go in `src/index.css` with `@theme`.
- **Rust is a Cargo workspace** rooted at the repo (`crates/{build-support,cli,core,keychain,ops,shim}`, `src-tauri`), with one `target/` at the root. Use `cargo fmt --all`. Release profile settings live in the root `Cargo.toml`.
- **Tests are lean**: one test per rule, each catching a distinct real regression. No permutations of one path, no re-testing what another file owns (the accent matrix lives in `health.test.ts`, verdict actions in `verdict.test.ts`), no tests of trivial getters, constants, registry data or one-line fallbacks, no snapshots. Prove coverage with a few deliberate breaks rather than more tests, and brief any test-writing agent with this bar and ask it to list what it dropped.
- **Docs voice is expressive**, like the always-up-to-date repo's: emoji section headings, emoji-led feature bullets, badges, a centered logo, screenshots, the Buy Me a Coffee link and the "MIT © Tyler Robertson @ Pixel Perfect Software Inc." license line. Don't tone it down to "plainer" prose (that is the voice of CLAUDE.md and DESIGN.md, not the docs). An emoji heading changes its GitHub anchor (`## 🚀 Build and install` is `#-build-and-install`), so update in-repo links.
- **Workflows pin every action to a release's full commit SHA**: see `.github/CLAUDE.md`.
- **Rust tooling:** `rust-toolchain.toml` pins 1.100.0 (rustup reads it; Homebrew Rust doesn't, so match it by hand). `[workspace.lints]` denies `unsafe` (denied, not forbidden, so the two FFI modules, `crates/keychain/src/store/windows.rs` and `src-tauri/src/traffic_lights.rs`, can allow it, arguing each call's safety) and adds a curated slice of clippy pedantic; every member opts in with `[lints] workspace = true`. `cargo deny check` (`deny.toml`) allows permissive licences only, so no GPL code can arrive through a dependency, and checks RustSec advisories, for all four shipped targets (the triples in `packaging/notices/about.toml`; keep the two lists equal), on every code change and weekly for `main` and the latest release (`advisories.yml`, with `main`'s `deny.toml`). An advisory with a published fix is bumped to the fix, waiting for the registry if cargo can't see it yet (never hand-write lockfile entries); an ignore is only for an unmaintained crate with no way out, and needs a reason naming the dependency that holds it in and what ends it. `cargo machete` finds unused dependencies. CI runs all of them.

## Git workflow

- The default branch is `main`. All work goes through pull requests, never a direct push to `main`; merged PRs in the history are merged into `main` with a merge commit ("Merge pull request #N").
- Branch names, from the merged PRs: `fix/<issue>-<slug>` and `feat/<issue>-<slug>` for work on an issue (`fix/199-render-saved-applies-registry`), `release-<x.y.z>` for a release (`release-0.11.0`), and `m4-plan`, `m8-plan` or `close-m3` for roadmap-only changes.
- `/ship:pr` opens a pull request. `/ship:release` opens the release PR: a `release-<x.y.z>` branch with a "Release <x.y.z>" title.
- The user merges, with `gh pr merge <n> --merge --admin --delete-branch` (PRs are opened from the user's own account and `main` needs a review, so the merge is an admin bypass). Auto mode blocks an agent's `--admin` merge. Admin merges skip the required checks, so a PR is ready only once its CI is green: watch it first, and test anything that runs a shell under `SHELL=/bin/bash` too (macOS runners' `/bin/bash` is 3.2, which lacks `BASH_ALIASES` and more, while the dev Mac's default shell is zsh).
- "Automatically delete head branches" is off, and deleting a base branch (`--delete-branch`, `git push --delete`) closes every PR stacked on it; GitHub doesn't retarget them. Retarget a stacked PR (`gh pr edit <n> --base main`) before its base merges, branch from `main` rather than stacking unless there is a real dependency, and after a stack merges check that each commit is on `main` (`git merge-base --is-ancestor <sha> origin/main`) and each issue is closed.
- After the release PR merges, the user tags `v<version>` on the merge commit (v0.11.0 is the merge commit of #201). Never push a tag yourself.
- The version lives in the root `Cargo.toml`'s `[workspace.package]`, which every crate inherits (`version.workspace = true`) and the app takes too (`tauri.conf.json` names none, so Tauri reads `src-tauri`'s), and in `package.json`. The tag must equal both (`cargo metadata` must show one version), be on `main`, and name a commit CI passed on: the `check` job (`.github/scripts/ci-passed.sh`) waits for that commit's CI run and refuses one that was cancelled or failed or never ran, so tag the merge commit, not a branch commit. CI runs on `main` are grouped by commit (`concurrency.group` is the SHA there, the branch on pull requests), so a later push never cancels or replaces one, queued or running.

## Gotchas

- **Tests must never touch the real home directory.** Shell code resolves startup files from the `home` it's given, and finds zsh's `ZDOTDIR` by asking a fresh zsh, never from the process environment. Don't read `ZDOTDIR` or `HOME` from `std::env` in testable code. Claude Code's own environment sets `ZDOTDIR`.
- **Shell startup files, setup status, the login shell's answer and `check_folder`**: see `crates/ops/CLAUDE.md`.
- **The shim and helper build, icons and signing**: see `src-tauri/CLAUDE.md`.
- **Review the UI in a browser, never against the real home folder.** `pnpm dev` and then `http://localhost:1420/?scenario=first-run|populated|mcp|shadowed|broken` (add `&platform=linux` or `&platform=wsl` for those systems, and `&check=`, `&shim=stale` or `&store=off` for states a real machine can be in; docs/contributing.md lists them) runs the frontend with every Tauri call answered by `src/dev/mockTauri.ts` (dev-only; `window.__mockDrop(path, x, y)` simulates a Finder drop). Keep the mock answering as the real backend does, with fresh objects each call: a check in a shell that's off returns `shadowedOnPath`, not `notFound`, whenever the tool is installed. `src/dev/mockTauri.test.ts` pins the mock's answers that mirror backend messages. Running the real app touches `~/.envrouter`, and its shell toggles edit the real startup files. To try the real app safely, launch the built binary with `HOME` set to a scratch folder. Every run of any EnvRouter binary gets a scratch `HOME`, `--version` included.
- **`target/debug/envrouter` may be the app, not the CLI.** The app crate and the CLI crate both build a binary named `envrouter`, and whichever built last wins, so running it can open a debug window against the real home and replace the installed shim and Keychain helper. Run the CLI only as `cargo run -q -p envrouter-cli -- …`. With `HOME` overridden cargo looks for its registry and toolchain under the scratch home, so pass the real ones: `env CARGO_HOME="$HOME/.cargo" RUSTUP_HOME="$HOME/.rustup" HOME=<scratch> cargo run -q -p envrouter-cli -- …`.
- **Wire types live in `src/lib/types.ts`.** Rust tests pin the JSON (`wire_format_matches_the_typescript_types` in `shell.rs` and `editors.rs`; the rpc envelope in `rpc.rs`), so change both sides together. Commands reject with a message string, except `get_config`, which rejects with a `ConfigFault` (`{ kind, message }`; over rpc the response carries `errorKind` beside `error`), because the window offers Back Up and Start Over only for a config.json that won't parse (`ErrorKind::Parse`), never by matching message text.
- **Check Linux and Windows from a Mac with `dev/containers/compose.yaml`** (Podman or Docker, project `envrouter-dev`): `linux-test` (backend tests with every shell required, and a GNOME Keyring round trip), `linux-app`, `linux-bundle` (the `.deb` and AppImage as the release builds them), `windows-helper-build` then `windows-helper-wine` (the Credential Manager round trip under Wine, a test-only Windows compatibility layer; only Wine runs emulated, since qemu crashes Rust tooling). The shell tests skip a missing shell, except under `ENVROUTER_REQUIRE_SHELLS=1`, which CI and the containers set.
- **`XDG_CONFIG_HOME` counts only inside the given home** (`platform::xdg_config_home`), so a test's scratch home can't reach the real config folder.
- Never read `.env` files. Ask the user for variable names instead.
