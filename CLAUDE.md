# EnvRouter

@.claude/context/ai-context/docs-overview.md

EnvRouter is a desktop app (Tauri v2) for macOS and Linux, WSL 2 included (native Windows is
planned), that does two things per folder for coding agents
(Claude Code and Copilot CLI): it sets the agent's config variable, so `claude`
run in `~/dev/work` uses a different `CLAUDE_CONFIG_DIR` than in `~/dev/personal`, and it hands
the agent a set of **MCP servers**. The user defines **profiles**: each one maps trigger folders to
a variable per tool and a selection from the MCP **server library**. Profiles are stored in `~/.envrouter/config.json`. A headless CLI, `envrouter`, does the same
setup without the window (servers, WSL distros, scripts).

**Distribution.** There's deliberately no paid Apple Developer ID, so no Developer ID signing or
notarization: the macOS app is signed ad hoc and installed with Homebrew (`brew install --cask
pixel-perfect-software/tap/envrouter`; the cask clears the quarantine flag). Linux gets a `.deb`
and an AppImage from the GitHub release; the CLI installs on both with `brew install
pixel-perfect-software/tap/envrouter-cli`. Pushing a `v*` tag runs `.github/workflows/release.yml`:
macOS and Linux (x86_64, aarch64) builds, one release with `SHA256SUMS`, then
`packaging/homebrew/render.sh` fills the cask and formula templates in `packaging/homebrew/` and
pushes them to the separate `homebrew-tap` repo with the `TAP_TOKEN` secret (a fine-grained
token, Contents read and write on `homebrew-tap` only), so the tap holds only generated files.
EnvRouter is GPL-3.0-or-later; every bundle and CLI archive carries `LICENSE` and
`THIRD-PARTY-NOTICES.txt` (`pnpm notices`, from `packaging/notices/`; CI runs it so a dependency
with no licence text fails there, not at release). Dependencies stay permissive (`deny.toml`).
The version lives in the root `Cargo.toml`'s `[workspace.package]`, which every crate inherits (`version.workspace = true`) and the app takes too (`tauri.conf.json` names none, so Tauri reads `src-tauri`'s), and in `package.json`. The tag must equal both (`cargo metadata` must show one version), be on `main`, and name a commit CI passed on: the `check` job (`.github/scripts/ci-passed.sh`) waits for that commit's CI run and refuses one that was cancelled or failed or never ran, so tag the merge commit, not a branch commit. CI runs on `main` are grouped by commit (`concurrency.group` is the SHA there, the branch on pull requests), so a later push never cancels or replaces one, queued or running.

**How it works: shims, like mise or volta.** `~/.envrouter/shims/<tool>` is a symlink to
`~/.envrouter/bin/envrouter-shim`, a small Rust binary, and a marked block in the user's shell
startup files puts `shims/` first on PATH. On each run the shim reads `config.json`, picks the
profile for the current folder, sets that tool's variable, adds that profile's MCP servers to
the command line, and `exec`s the real tool found later on PATH. Config edits apply on the next
run in every terminal, with nothing to reload.

**Editor extensions** that run their own copy of an agent (Claude Code for VS Code) bypass PATH,
so they're routed through their process-wrapper setting: the editor runs `envrouter-shim <its
binary> <args>`, and the shim's wrapper mode routes that binary (`crates/shim/src/main.rs`,
`wrapped`). Builds that ship a script instead (Claude Code for VS Code without a native binary,
like 2.1.89's universal build) pass `<interpreter> <script> <args>`, with VS Code's own Electron
helper as Node; the agent is the one whose `ide.extension` names the installed folder
(`<id>-<version>[-<platform>]`) holding the script, and injected arguments go after the script.
`crates/ops/src/editors.rs` sets the setting in VS Code-family user settings (JSONC kept intact,
written through symlinks, never replacing someone else's wrapper) and in remote servers' machine
settings (`~/.vscode-server/data/Machine/settings.json`), which is what
VS Code on Windows reads for a WSL folder. The hook is agent data: `ide` in `src/lib/agents.json`,
saved to `config.agents.*.ide`.

## Where the code lives
- `crates/core`: the config model, routing, MCP rendering, and `platform.rs`, the one place that
  answers what differs between macOS, Linux, WSL and Windows. Callers ask it a question; they
  don't check the OS.
- `crates/ops`: the backend with no UI. `ops::commands` holds the body of every window command;
  `src-tauri/src/lib.rs` wraps each one (adding only the tray and the async runtime), and
  `ops::rpc` serves the same ones by name to `envrouter rpc`, one JSON line each way, the bridge
  a window will use to manage a WSL distro (`wsl.exe -d <distro> -- ~/.envrouter/bin/envrouter
  rpc`). A new command goes in all three; a test pins `rpc::COMMANDS` to the window's handler list (`window_commands!` in `lib.rs`). `open_in_editor`, `open_help` (one of two fixed pages of the repository, named by `help::Link`, opened through the opener's Rust API, so the window needs no `opener:allow-open-url` and can't ask for any other address; the Help menu opens the same list from a thread of its own (`tray::help_in_background`, which asks for no home folder, so Help works after an uninstall), and a failure comes through the `reveal-failed` event, so it shows in the window's banner as a menu bar reveal's does, while a success leaves the window where it was; a test holds every address under the repository and `src/lib/helpLinks.json`, which the mock uses, to the Rust list. Only a launcher that can't start is reported off macOS: `help.rs` says why) and `reveal_place` (which shows one of EnvRouter's own places, `commands::Place`: config.json revealed, `~/.envrouter` or a profile's MCP folder opened, or a trigger folder revealed (`Place::Trigger`, which `locate` holds to the saved config's trigger folders and the folders inside them, so the window still can't ask for an arbitrary path; one that's gone (a link to nothing counts) is told as "There's no … any more" there, config.json that can't be read as "Couldn't check … against config.json", and one the saved config no longer names as "isn't a trigger folder any more", and the window offers no Reveal for a trigger the backend wouldn't accept (`isValidBase`), not as the opener's "No such file or directory (os error 2)", which it also gives when it can't reach the file manager), through the opener's Rust API so the window needs no capability for it; the menu bar's Reveal config.json and Open ~/.envrouter call the same `show_located`, which opens only a real folder (a file, or a link to one, is refused, since the system would run it), and, on a failure, show the window with the reason through the `reveal-failed` event unless an uninstall has begun) aren't served over rpc, nor are the app-lifecycle commands `set_unsaved_edits` and `quit_app`, which live only in `src-tauri`.
- `crates/cli` (`envrouter`), `crates/shim`, `crates/keychain` (secrets), and
  `crates/build-support`, which builds the shim and helper for the build scripts that bundle or
  test them.
- **`uninstall`** (`ops::uninstall`, `envrouter uninstall [--yes] [--dry-run]`, the Shells popover and the tray) runs shells, editors, the secret item, `~/.envrouter`, then the app's webview folders (`platform::app_data_dirs`, for the current `APP_IDENTIFIER` and then every `LEGACY_APP_IDENTIFIERS` entry, so a machine that updated from an older release is cleared too, and `defaults delete` runs for each domain: macOS `~/Library/{WebKit,Caches,HTTPStorages}/<identifier>`, `Saved Application State/<identifier>.savedState` and `Preferences/<identifier>.plist` and `Application Support/<identifier>`, which the cask's `zap` also lists for both identifiers (and its `uninstall quit:` the bundle ids), a test keeps them equal; Linux `$XDG_DATA_HOME` (or `~/.local/share`)`/<identifier>`, the `app_local_data_dir` Tauri forces as the webview's data folder on Linux and Windows (`tauri/src/manager/webview.rs`), where wry also points WebKitGTK's cache, so it is the one folder (observed by running the built app under Xvfb with a scratch HOME); Windows `AppData/Local/<identifier>`, from the same source; the app never asks for Tauri's `app_data_dir`, `app_cache_dir` or `app_log_dir`, so none exist, but its `app_config_dir` (`<config dir>/<identifier>`: macOS `Application Support`, Linux `$XDG_CONFIG_HOME` or `~/.config`, Windows `AppData/Roaming`) holds the window-state plugin's `.window-state.json`, so it is the last folder of each list; an `XDG_DATA_HOME` or `XDG_CONFIG_HOME` outside home isn't trusted, so its folder isn't deleted, only named in `app_data_left`, with the values read by the caller and passed in as `platform::XdgHomes`); a problem in the first two stops it before anything irreversible. Step 5 is housekeeping: a folder it can't delete is a sentence in `app_data_left`, never a `problems` entry, so `finished()` (and with it the rpc `Session` ending and the quit) reflects steps 1 to 4 only; `forget_preferences` runs `defaults delete` first on macOS because `cfprefsd` caches the domain and could write a removed plist back, with the file deleted too as the fallback. **The window's own run (`Caller::App`) leaves those folders**, since its live webview holds them and writes them until it quits: `finish_uninstall` in `src-tauri/src/lib.rs` deletes them on `RunEvent::Exit` (after `UNINSTALL_FINISHED`), verified under Xvfb in the Linux container (the folder is gone and stays gone after exit; the control run without an uninstall leaves it); on macOS this is reasoned, not run. Link targets that a deleted link pointed to, for `~/.envrouter` and these folders alike, are `report.left` (`{link, target}`). It's served over rpc with a **required** `dryRun`, so the `{}` dispatch test can't run a real one; a finished real run ends that rpc `Session` (it answers nothing more, so a remote window can't recreate the folder). Nothing may recreate `~/.envrouter` afterwards, so: in the app, `home()` in `src-tauri/src/lib.rs` counts every command in until it finishes (`Gate`, the `Lease` inside the `Home` it returns), and a real uninstall raises the gate (later commands are refused), waits up to 5 s for the commands already running (a slow MCP check, a queued save) and doesn't run if they don't finish; the gate stays up only when the uninstall finishes. For the CLI, the app holds an advisory lock on `~/.envrouter/app.lock` for as long as it runs (`uninstall::hold_app_lock`), and a real `envrouter uninstall` (or rpc one) refuses with "Quit EnvRouter first (…)" while it's held, before changing anything; the app's own uninstall isn't checked. The lock is per home, so in WSL, where a Windows window isn't in the distro, nothing is falsely refused; a window on Windows that manages a distro over rpc must stop reading after it ends the session (M7).

## How MCP servers reach an agent (`crates/core/src/mcp.rs`)
- **No gateway or daemon.** On every save the app renders, per profile and per agent with an MCP descriptor, one config file per server in the agent's dialect plus a `launch.json` manifest, under `~/.envrouter/mcp/<profile id>/<command>/` (files 0600, folder 0700). The shim reads only the manifest and adds its arguments ahead of the user's own. A save removes a manifest it no longer renders at once, but a server file only 10 minutes after it stopped being named (`mcp::RETIRED_GRACE`, timed in `~/.envrouter/mcp-retired.json`), at a later save: a run that read the old manifest just before the save opens that file as the agent starts.
- **Always the `--flag=value` form.** Claude's `--mcp-config` and `--disallowedTools` take several values, so `--mcp-config <file>` as two arguments swallows the next one (`claude --mcp-config f mcp --help` breaks; `--mcp-config=f mcp --help` works, verified on 2.1.303). `config::validate` rejects a descriptor without the `=`. `claude mcp list` never shows flag-injected servers. Copilot (verified on 1.0.98) takes `--additional-mcp-config=@<file>` (repeatable, added to the user's own servers) and turns a tool off with one `--deny-tool=<server>(<tool>)` per tool; `copilot mcp list` doesn't show injected servers either. Copilot expands `${VAR}` in env and headers, not args, so a stored secret belongs in an env var or header there.
- **`npx` servers are rendered with `--prefix=<home>` first** (`mcp::launch_args`). Agents start servers in the project folder, and npm 11 refuses to run (`EBADDEVENGINES`) in a project whose `package.json` pins another package manager under `devEngines`. The prefix moves only where npm looks for a project; the server still runs in the folder. Claude ignores a `cwd` field in a server config (verified), so moving the server isn't an option. `config.json` keeps what the user typed.
- **Secrets live in one item in the platform's store** (`crates/keychain`, `src/store/`): the login Keychain on macOS, the Secret Service (GNOME Keyring, KWallet) on Linux, the Windows Credential Manager on Windows and inside WSL, where the Linux side runs `envrouter-keychain.exe` over interop through its `store-get`/`store-set`/`store-delete` bridge (exit 3 means none; keyed by distro and home). A Credential Manager credential holds at most 2,560 bytes, so the item is split across numbered parts. With no store, every call says so and a server needing a secret is left out. The item is keyed by the canonical home folder, so scratch-HOME runs and tests never see the real one. Rendered files refer to `${ENVROUTER_SECRET_<ID>}`. **The window asks whether the store is usable without using it**: `setup_status` carries `secretStoreProblem` (`envrouter_keychain::problem`, each store's `usable`), asked on every focus, so it reads, writes and unlocks nothing and never prompts. macOS and Windows answer `Ok` (nothing can be known without asking the store); the Secret Service opens a plain session and reads the `default` alias; WSL runs the Windows helper with no arguments (usage only). Both run one check at a time on one thread (`envrouter_core::watcher::Watcher`): the first ask waits up to 3 s, a store that hasn't answered by then is *unknown*, not missing (no problem, the lock stays on), and an ask made while a slower check is still running gets the last answer at once, so a hung D-Bus never piles up threads or holds up every refresh. With a problem (`platform.canLock` false) the editor disables the lock and shows values as plain text; `serverOf(draft, canLock)` is the one place that saves a value marked for the store as plain text then (see DESIGN.md "Keychain value"). **The shim never links the Security framework**: loading it cost ~1.4 ms on every launch (measured), so the shim runs the `envrouter-keychain read <ids>` helper, installed beside it, only when a server needs a secret (20s timeout), reads the values from its stdout and sets them on the agent. Keep `crates/core` and `crates/shim` free of any store library; `otool -L` on the release shim lists only `libSystem`, `ldd` only libc and libgcc. The helper's `read [ids]` contract (one JSON line on stdout, non-zero with the reason on stderr) is what the shim depends on; keep it. Secret values are never in argv, `config.json` or a rendered file. Typed values travel only with `save_config(payload, secrets)` (the window's Save, or `envrouter secret set <ID>`, which reads the value from stdin or a no-echo prompt), which stores them before writing the config and, once it is written and rendered, drops the secrets nothing names. A secret that a Start Over backup (`config.json.bak`, `.bak-2`, …) still names stays until the backup goes (`config::backed_up_secret_ids`), so putting the backup back brings its servers' secrets with it. The store is read only when a save adds or drops a secret, and one that won't drop a secret gives the save a `warning` (`SaveOutcome::Saved`; the window shows it, the CLI prints it) rather than failing a save whose config is already written; the next save that reaches the store drops it. The window never gets a value back. After installing a new helper while secrets are in use (on save, or at launch after an update), the app runs `envrouter-keychain read` once, so macOS asks for access while the app is in front.
- **Checking a server** (`crates/ops/src/mcp_probe.rs`, on the official `rmcp` crate) runs only when the user clicks: it starts the server with a new terminal's PATH (`shell::login_path`, since an app launched from Finder or a `.desktop` file may have a bare one; kept for 3 minutes per home, and a server check the user clicks takes one no older than 30 s, `login_path_recent`; the npm lookup uses the kept one), lists its tools, and stops it. It opens with `initialize` at 2025-11-25, which every server before MCP 2026-07-28 answers; one that refuses it with a JSON-RPC error, as a server speaking only 2026-07-28 does, is started once more and asked with `server/discover` (10 s), and if that fails too the check reports the first answer. Not rmcp's `Auto` mode: its fixed 10 s probe runs out while a first `npx` run downloads, and the late answer then fails the `initialize` it falls back to. Tool lists from good checks are cached in `~/.envrouter/mcp-tools.json` with the definition they came from, and only offered while it matches. Checks run side by side, so the cache is edited under `mcp-tools.lock`, and a save prunes servers the library dropped. rmcp has no legacy SSE client, so SSE servers report `unsupported`. Tool filtering is a deny list (`disabledTools`), rendered for Claude as `--disallowedTools=mcp__<server>__<tool>`.
- **Import only reads** (`crates/ops/src/mcp_import.rs`): each agent's own MCP files, located by its `mcpFiles` descriptor in `agents.json` (Claude: `.claude.json` in `~` and each profile's config folder, including its `projects` tables, plus `.mcp.json` in trigger folders). Credential-looking env and header values (`SECRET_NAME` in `src/lib/mcp.ts`, or a URL with a password in it) are moved to the secret store on import; `${VAR}` references stay as typed, and so do arguments, since Copilot doesn't expand a secret there. **Paste JSON** (`mcp_import::parse_pasted`, the `parse_mcp_json` command) reads the same entries from pasted text, JSONC included, and goes through the same review. The catalog (`src/lib/mcpCatalog.ts`) is written from each vendor's README.
- **Pinning an `npx` server** (`src/lib/npm.ts`, `crates/ops/src/npm.rs`): the editor reads the package from the arguments and, on a click (or on opening a catalog pick), asks the user's own npm (`npm view <name> dist-tags --json`, the npm beside the server's `npx`, login PATH, run from home) for its tags, then writes `<name>@<version>` into the argument. Only an exact version counts as pinned. Containers and `uvx` aren't covered yet.
- A profile's servers go to every agent with a descriptor, even if the profile leaves that agent's folder alone, so `config::tool_names` gives those agents shims too.

The window has two views, switched in the titlebar (⌘1, ⌘2; Ctrl off macOS). **Profiles** is built around a
direction called **the Sorting Frame**: one card per profile with its folders filed inside,
rendered as modern layered Mac cards (the user asked for clearly separated surfaces, so don't
regress to flat ruled grids), with a profile's editor as a right-side inspector. **MCP Servers** is
a list beside the server editor, with Catalog and Import in the same detail area. Assigning a
server to a profile works from both sides (the profile's MCP checklist, the server's Used by
toggles), so keep both. Before changing the UI, read `PRODUCT.md`,
`.impeccable/surfaces/src-app-tsx.md` (the direction contracts) and `DESIGN.md` (tokens and
rules: one accent button per state, status-free profile colours). The window is translucent
over macOS under-window vibrancy (`transparent` and `windowEffects` in `tauri.conf.json`; the
private API a transparent window needs has been always on since Tauri 2.12.1, so there's no
`macOSPrivateApi` or `macos-private-api` feature): only the ground lets it through,
cards stay opaque, and the browser mock shows the solid ground. The app also lives in the menu
bar (`src-tauri/src/tray.rs`), whose menu refreshes when the window gains focus and when the pointer reaches the icon (macOS, Windows), so a CLI change or hand edit shows; on macOS closing the window only hides it. The menu also holds **Check Last Folder** and a disabled version line (`EnvRouter 0.8.0`, from the package version). "Last" is the folder of the window's latest `check_folder`, kept in `~/.envrouter/last-folder.json` (`ops::last_folder`): the window's `localStorage` isn't readable from Rust, and the file goes with `~/.envrouter` on uninstall. The item is disabled while there is none or the folder has gone, and chooses by leaving a `MenuRequest` for the window (the same way "Check Folder…" does): the request waits in the backend (`tray::MENU_REQUEST`) and the window takes it (`take_menu_request`) when it hears `menu-request` and once as it starts listening, since an event sent before the webview listens (the first show after a hidden launch, a reload) is lost; it waits for config.json to be read, then checks the folder as a drop does, or says why it can't (the profile editor is open, config.json can't be read). **The window comes back where it was** (`tauri-plugin-window-state`, with `SIZE | POSITION | MAXIMIZED` only: not `VISIBLE`, or a window hidden to the menu bar when the app quit would never open again, and not `DECORATIONS`, which the platform config owns). The plugin saves at exit, and EnvRouter saves again when the macOS close hides the window, so a crash or force quit loses little. Its file, `.window-state.json`, is in the app's config folder (see the uninstall bullet), not in `~/.envrouter`, and that folder is in `platform::app_data_dirs`, so both the CLI's uninstall and the app's exit-time `remove_app_data` delete it (the plugin saves on `RunEvent::Exit` before the app's own callback, which deletes it after). **The bundle identifier is `ca.pixel-perfect.envrouter`; the one before it (`platform::LEGACY_APP_IDENTIFIERS`, the only place the old name is written in code, besides the cask) is cleaned up at launch** by `leave_legacy_identifier` in `src-tauri/src/lib.rs`, a plugin added before window-state so it sets up first (plugins start in order). It copies the old `.window-state.json` into the new config folder when the new has none (`ops::legacy_identifier::carry_window_state`, synchronous, since window-state reads its file while it starts, and read-only on the old side). Then a thread runs `clean_up_old_identifier`, which keeps `.legacy-cleaned` in the new config folder (`done`, or the number of launches that left something, three at most): with no legacy folder on disk it just notes `done` (a fresh install asks nothing of the system); while another process of this user (`platform::user_processes`: `/proc` owned by the uid on Linux, `ps -U <uid> -x` on macOS) runs the app's binary (`platform::is_app_binary`; 0.7.2 and before don't hold `app.lock`, and an AppImage, `.deb` or copied app isn't quit by the cask) it does nothing and notes nothing, so a later launch retries (a process list it can't get is logged and counts as not running); otherwise it deletes the legacy identifier's webview data, caches, saved state, preferences and config folder (`uninstall::remove_legacy_with`, over `AppData::legacy`) and runs `defaults delete` for the old domain, and notes `done` only if nothing was left. What it leaves (an undeletable folder, one under an `XDG_*` outside home, a deleted link's target) goes to stderr and counts a try; the uninstall names the leftovers again. The webview's storage can't move (WKWebView and WebKitGTK key it by identifier), so the last view resets once. First-run's last step used to live in that storage too (`envrouter.checkedOnce`); it is now the backend's: `commands::check_folder` writes `~/.envrouter/checked-once` (`ops::checked_once`) the first time a check comes back routed, `SetupStatus.checkedBefore` reports it, and `healthOf` counts it. For an install set up under the old identifier, `legacy_identifier::carry_checked_once` writes it in the plugin's setup (file reads only, so before the window's first status) when an old folder exists, `config.json` has a profile and a startup file holds the shell block: it was plainly set up, which is all the old answer meant. Nothing else is derived from the identifier here: the Linux `.desktop` file, its `StartupWMClass` and the AppImage take `mainBinaryName` and `productName`, GTK's app id is off (`enable_gtk_app_id`), and the tray id is its own constant. The Keychain secrets item is keyed by service and home, and the helper's access is granted to its ad hoc `cdhash` (its code-signing identifier is `envrouter-keychain-<hash>`, not the bundle id), so a new identifier neither moves nor re-prompts it beyond what any update that changes the helper does (`ask_keychain_access`). The window never calls the plugin's commands, so `capabilities/default.json` grants none of its permissions. The last view (Profiles or MCP Servers) is `localStorage` (`src/lib/lastView.ts`). **Quitting with unsaved edits asks first** (`src-tauri/src/quit.rs`): the editors report their dirty state (`src/lib/unsaved.ts` → `set_unsaved_edits`), and the menu bar's Quit, ⌘Q and closing the window off macOS come through `ExitRequested` or `CloseRequested`, which ask the window (`quit-requested`) only while it holds edits; a second quit it hasn't answered goes ahead. macOS's predefined Quit can't be asked (tao handles only `applicationWillTerminate`), so the app menu's Quit is EnvRouter's own item (`menu::app_menu`); the Dock's Quit still terminates. That menu also holds Settings… (⌘,) after About and the Help menu's links (`src-tauri/src/menu.rs`, `help.rs`): there's no Preferences window (PRODUCT.md, principle 1), so Settings… and ⌘, (Ctrl+, off macOS, where there's no menu bar) open the Shells popover, from any view, but not with the profile inspector open, while an uninstall runs, or with no shell to show (the control they stand for is absent); the Shells popover also carries the Documentation and Report an Issue links, which is where Linux and WSL reach them. A server editor holding edits isn't remounted by a reload that changed its server; it says so instead.

**Off macOS the window follows the system** (`src-tauri/tauri.linux.conf.json`, DESIGN.md
"Platform chrome"): native decorations, an opaque window, no traffic-light inset, Ctrl
shortcuts, the store called "keyring" ("Credential Manager" inside WSL), and closing quits, since GNOME has no tray to come back
from. The frontend reads the platform from `SetupStatus.platform` through `usePlatform()`
(`src/lib/platform.ts`); add a platform difference there, not with an inline check. Wording and
paths come from the backend rather than the window: `SetupStatus` carries the store's name, the file manager and its
reveal verb (`Platform::file_manager`, `reveal_verb`, which also word the menu bar) and `shimPath`, a `ConfigFault`
carries the unreadable file's `path`, and each `EditorStatus` its `label`. Only what must be right at the first paint,
before the status arrives, is guessed from the user agent (`ownsTitlebar`, `vibrant`), with defaults for the words that
the backend's replace, kept in `src/lib/platformWords.json` (the browser mock answers from it too; a test in `platform.rs` holds
it to what `Platform` says, so change both together). A failed `get_config` names the file in `ConfigFault.path`, and over
`envrouter rpc` in `errorPath`. Nothing builds a `~/.envrouter` path or keeps a copy of the editor list. On Linux
the app's binary is `envrouter-app`, so `envrouter` is always the CLI.

## How routing resolves (`crates/core/src/resolve.rs`)
- **The most specific profile wins outright.** The deepest trigger containing the folder picks the profile. If that profile doesn't configure the tool, the tool runs with **no** override; it never falls back to a shallower profile. The user chose this deliberately.
- **Compare canonical paths, never `$PWD` text.** `$PWD` keeps typed symlinks and letter case (`~/Dev` on a case-insensitive volume), so both the folder and each trigger go through `fs::canonicalize`.
- **Triggers are whole-subtree prefixes.** `~` is expanded and a trailing `/*` or `/**` is dropped (`config::trigger_base`); any other `*` is rejected. `config.json` keeps what the user typed.
- **A save names its base.** The window passes the config its edit started from; `commands::save` (under `config.lock`, which the CLI's saves take too) refuses it with `changed` and the file as it is now when they differ, before touching the secret store. The window then merges per profile and per server (`src/lib/merge.ts`) and asks (`confirmReplace`) only when both sides changed the same one. The CLI's saves (`commands::save_from_cli`) name the file they read as their base too, and on `changed` read it again and redo their edit (up to three tries), so a window save in between is kept.
- **`config::validate` runs on every save.** It rejects a folder claimed by two profiles, tool or env var names that aren't strict identifiers, and a tool folder that isn't absolute or `~`-based (a relative one would resolve against wherever the tool runs; `resolve` skips one from a hand-edited config too). Tool names become file names in `shims/` and are interpolated into shell probes, so keep `is_command_name` strict.

## The shim must never block the tool
It also must stay cheap: it runs before every agent launch. CI's `shim-timing` job fails when, with 60 triggers and 8 PATH entries ahead of the tool, its median launch takes over 1.8x a bare exec's (`.github/scripts/shim-overhead.sh`; a ratio because runner machines differ in speed, on Linux because macOS runners' timings swing 16x). Match triggers and PATH entries by one `stat` each, not `canonicalize`, which walks every component.

A missing config means the tool runs silently. A broken one prints a warning and the tool still runs. The same goes for MCP: no manifest means no injection, a broken one warns, a server whose secret can't be read is left out with a warning, `--strict-mcp-config` (or `ENVROUTER_MCP=0`) turns injection off for that run, and so does a first argument in the agent's `skipSubcommands` (Claude's background-session commands, `daemon` among them, read as a prompt with an option ahead of them, `remote-control` and its alias `rc` refuse one, its hidden aliases `remote`, `sync` and `bridge` read as a prompt too, and `claude plugin test` refuses any option before `plugin`; swept on 2.1.309, the aliases on 2.1.310, the list and reasons beside the import in `tools.ts`), and so does an existing file in its `skipIfPresent` (Claude's enterprise `managed-mcp.json`: Claude Code exits at startup when it's given servers on a managed machine), with one warning, which explain mode and `check_folder` report as `mcpManagedBy`. Explaining never asks the secret store. When looking for the real binary, the shim skips the shims directory, empty PATH entries (the current directory), and anything that canonicalizes to itself, so it can never exec itself in a loop. A wrapper further along PATH that looks there for the tool, skipping only itself (VS Code's `copilot-shim`), would bring it back: the shim leaves its process and parent IDs in `ENVROUTER_SHIM_RAN`, which exec keeps, and, run again in that same process, runs the same program once more with nothing added and every folder holding a shim for the tool taken off PATH (`programs::without_shims`), so the wrapper finds the tool itself or gives its own answer. In wrapper mode (run under its own name, for an editor) it wraps only an absolute path to an executable that isn't a shim; one it can't name as a tool (not named like a command, and not running a script from an agent's extension) runs unrouted with a warning rather than not at all. Keep these properties; `crates/shim/tests/shim.rs` covers each one.

## Constraints
- **No logins or OAuth.** EnvRouter never signs anyone into an agent or an MCP server; agents run their own sign-in (`/mcp`). The one credential it handles is MCP secret values the user enters, kept in the secret store item above.
- **Tauri v2 APIs only.** v1 examples (`tauri.conf.json > allowlist`, `@tauri-apps/api/fs`) are wrong here. Use plugins and `capabilities/*.json`.
- **All file access happens in Rust commands.** There's deliberately no fs plugin, and `capabilities/default.json` grants only the two plugin calls the window makes (dialog open, dialog message), one by one; links open from Rust (`help::open`), never through the plugin's `allow-open-url`. Don't go back to a plugin's `:default` set, and don't add `@tauri-apps/plugin-fs` back. `build.removeUnusedCommands` (`tauri.conf.json`) compiles out every plugin command no capability grants: the fs plugin, which the dialog plugin depends on, keeps none, and dialog keeps only the two, and the opener, registered for its Rust API, keeps none. So a new plugin call needs its permission here, or it isn't in the build at all (the app's own commands are never removed: there's no app ACL).
- **The window has a CSP** (`app.security.csp` in `tauri.conf.json`): scripts and styles from the bundle only, and IPC. Loading anything remote or adding an inline script means changing the policy on purpose.
- **Keep the data model tool-agnostic.** `Profile.tools` is a `Record<toolName, { envVar, path }>`. Nothing in Rust branches on an agent's name: agent behaviour is data in `src/lib/agents.json` (its variable, and an MCP descriptor naming a config *dialect*, a file format), which the window (`withAgents` in `tools.ts`) rewrites into `config.agents` on every save. The CLI (`envrouter_core::agents::with_agents`) only fills in agents the config doesn't name yet (and adds the registry's skip rules, `skipAnyArgs`, `skipSubcommands` and `skipIfPresent`, to agents it does name: each only turns injection off for a run it would break, and a rule a release adds wouldn't reach a machine with no window otherwise), saved by `apply` and used in memory by `install` and `editor`, so a CLI-only machine needs no window and a CLI a release apart never undoes the app's descriptors. CLI saves go through `save_from_cli`, which installs its own shim and helper only where the installed shim can't read the config version it writes: none, one that answers `envrouter-shim --config-version` with an older version, or one from 0.7.0 or earlier, which doesn't answer (after `brew upgrade envrouter-cli` the old shim stays in `~/.envrouter/bin`). Rust renders dialects, not agents. Add an agent with one entry in `src/lib/agents.json` (its `mark` slug names the logo `AgentMark` draws; none, or one `icons.tsx` doesn't know, gets a generic bot), and only after checking its docs: the variable must relocate logins too, not just settings; note quirks in the entry's `note`, and why-comments beside the import in `tools.ts`, since JSON can't hold them. A config that still names an agent the window no longer offers keeps loading, saving and routing. `save_config` creates missing agent folders inside home. Codex and Gemini CLI were dropped to keep the app focused; they're future add-ons (Codex: `-c mcp_servers.*` overrides with secrets through `env_vars`, and its MCP OAuth tokens are shared across `CODEX_HOME`s; Gemini: settings in a file named by `GEMINI_CLI_SYSTEM_DEFAULTS_PATH`, which shallow-merges `mcpServers`, and `GEMINI_CLI_HOME` holds a `.gemini` folder).
- **Bump `CONFIG_VERSION` in `config.rs`** for any change to the shape of `config.json`, and migrate older versions in `config::load`. The shim refuses configs from a newer version.

## Conventions
- **pnpm only, versions in `.tool-versions`** (asdf): Node 24.22.1 and pnpm 12.14.0. `packageManager` in `package.json` repeats the pnpm version for `pnpm/action-setup` and pnpm's own version switching, so bump both together; the workflows read Node from `.tool-versions` (`node-version-file`).
- **Biome, not ESLint or Prettier:** 2-space indentation, **single quotes, no semicolons**, 150-column lines. Don't copy the double-quote/semicolon style from Tauri docs. Run `pnpm format-and-lint:fix`.
- **Tailwind v4** through `@tailwindcss/vite`: no config file and no PostCSS; theme tokens go in `src/index.css` with `@theme`.
- **Rust is a Cargo workspace** rooted at the repo (`crates/{build-support,cli,core,keychain,ops,shim}`, `src-tauri`), with one `target/` at the root. Use `cargo fmt --all`. Release profile settings live in the root `Cargo.toml`.
- **Workflows pin every action to a release's full commit SHA**, with the version in a comment (`uses: actions/checkout@<sha> # v7.0.1`), and pin the tools they install (`cargo-deny@…`, Node from `.tool-versions`); `.github/dependabot.yml` proposes updates monthly. Checkouts set `persist-credentials: false` unless they push (only the release's tap checkout does), and the release workflow restores no caches, so what users install is built only from the tagged source. CI's `changes` job skips the other jobs for docs-only changes rather than `paths-ignore`, because branch protection requires the `linux` and `macos` checks and a skipped job counts as passing. For the same reason `linux` is a gate over the parallel `checks` (frontend, licences, notices), `rust` (backend tests, the Windows helper linked with mingw) `app-linux` (the app crate) and `shim-timing` jobs that runs with `if: always()` and checks their results: a gate skipped by a failure would let the merge through. The release builds each platform's app and CLI in parallel jobs, renders the notices inside each while it compiles (`tauri build --no-bundle`, then `tauri bundle --config src-tauri/tauri.licences.conf.json`), and restores no caches. The licences are bundle resources from that file, never from `tauri.conf.json`: tauri-build checks each resource exists when the app crate compiles, so listing the rendered notices there would break every `cargo build` of it. `pnpm bundle` (render, then `tauri build` with that file) is the local build that carries them. **No job installs packages while it runs:** the Linux CI and release jobs run in `ghcr.io/pixel-perfect-software/envrouter-ci` (`.github/ci/Containerfile`: Ubuntu 22.04 for its glibc, every package they need, rustup without a toolchain), pinned by digest like an action, because Ubuntu's mirror stalled jobs for up to 17 minutes. To change a package, edit the Containerfile, push the branch, build it there with `gh workflow run ci-image.yml --ref <branch>` (it builds by itself only on `main`), and put the digest it prints in `ci.yml` and `release.yml`. The package is private, so those jobs take `packages: read`.
- **Rust tooling:** `rust-toolchain.toml` pins 1.99.0 (rustup reads it; Homebrew Rust doesn't, so match it by hand). `[workspace.lints]` denies `unsafe` (denied, not forbidden, so the two FFI modules, `crates/keychain/src/store/windows.rs` and `src-tauri/src/traffic_lights.rs`, can allow it, arguing each call's safety) and adds a curated slice of clippy pedantic; every member opts in with `[lints] workspace = true`. `cargo deny check` (`deny.toml`) allows permissive licences only, so no GPL code can arrive through a dependency, and checks RustSec advisories, for all four shipped targets (the triples in `packaging/notices/about.toml`; keep the two lists equal), on every code change and weekly for `main` and the latest release (`advisories.yml`, with `main`'s `deny.toml`). An ignored advisory needs a reason naming the dependency that holds it in and what ends it. `cargo machete` finds unused dependencies. CI runs all of them.

## Gotchas
- **Tests must never touch the real home directory.** Shell code resolves startup files from the `home` it's given, and finds zsh's `ZDOTDIR` by asking a fresh zsh, never from the process environment. Don't read `ZDOTDIR` or `HOME` from `std::env` in testable code. Claude Code's own environment sets `ZDOTDIR`.
- **The shell block is POSIX sh** (`shell.rs`, `POSIX_BODY`), so it's safe when bash's login file is `.profile`. bash's files depend on the terminal (`bash_startup_files`): on a Linux desktop only `.bashrc`; where terminals start login shells (macOS, WSL), the first existing login file, and with none of them `.bash_profile` on macOS but `.profile` on Linux. Never create a `.bash_profile` on Linux: it hides the `.profile` distros source `.bashrc` from. It moves the shims directory to the front of PATH rather than skipping it when it's already there, because nested shells re-prepend `~/.local/bin`.
- **`SetupStatus.missingAgents` says which agents a new terminal has nothing to run for and no editor carries** (`crates/ops/src/installed.rs`): the registry's agents and any the config names, each there when a program of that name is on the login shell's PATH (found with `programs::find_real`, the function the shim itself uses, in `envrouter_core`, so the two can't disagree: not in the shims folder, not a link to a shim, not the current directory); when the shell has an alias for it whose first word (past `VAR=x` words and `command`/`builtin`) resolves the same way, an absolute path or on PATH (what can't be known without a shell, like `$HOME/x`, a relative path, or another alias or function, counts as there: the mark says "Not installed", so it must be right); when it has a function of that name, which always counts, since what it runs can't be known without running it (fish's aliases are functions, so they count too); an alias to a builtin, keyword, function or alias of the shell's, or past a modifier (`noglob`, `exec`, `time`…), counts: the same login-shell run asks the kind of the alias's program word; or when an editor's extension for it is installed (`editors::extension_installed`: Claude Code for VS Code carries its own copy, hook on or off). It stats files and never runs a tool. The exclusion is in the backend, so the window, `envrouter status --agents` and rpc give one answer, and the window marks exactly what it is sent. `null` means unknown, and the window marks nothing then (inspector, cards, welcome); a probe that fails says why on stderr once per failure period.
- **The login shell's answer is kept 3 minutes, not asked on every focus** (`shell::login_shell_report`, `LOGIN_REPORT_TTL`): running it runs every startup file the user has, and what those files source can't be followed by any list of files, so a time limit it is. The run is the folder check's own script, prompt hooks included (`Shell::prompt_hooks`, `Shell::start`, shared with `check_folder`, so a mise or direnv PATH reads the same in both), and reports the PATH and, per command, `whence -w`/`type -t`. Kept per home with the commands it was asked about; an ask for more commands, or an explicit fresh one, runs again for the union of those and the kept ones, so no answer is lost to a narrower one. Only one run is under way per home and asks meanwhile wait for its end, then look at what it found as any ask would (a per-home run counter tells their wake-up from another home's); a failure is kept 1 minute with its error kind (`Error::replay`) and stops any rerun in that time whatever commands are asked, except a server check's click, which may retry; the cache's mutex is never held while the shell runs. A server check, which the user asks for, wants a PATH no older than 30 s (`login_path_recent`, `LOGIN_PATH_FOR_A_CHECK`), so a few in a row share one run; the npm lookup (`npm_dist_tags`, which a catalog pick runs on its own) uses the kept PATH, since where `npm` is doesn't change in minutes. A program that lands in a folder already on PATH shows at once, since the walk along PATH happens on every ask. `setup_status` waits for the agent probe 1 s at most in the app (`core::watcher::Watcher`, the one-thread-per-key, last-answer-kept pattern the secret store check shares), asks the secret store side by side with it where that can block (`Platform::store_check_can_block`: Linux and WSL; a panic there is reported as a problem, not as none), and when a probe finishes after the asker gave up the app emits `setup-changed` so the window asks again; that ask is handed the answer the probe just found (a Watcher answer under 5 s old isn't probed for again, a panicked probe's "nothing" included), so it can't be late in turn, forever. rpc has no push line and one slow call holds up the lines queued behind it, so `get_setup_status` over rpc waits the same 1 s as the window and answers null if the shell hasn't (the session is one long-lived process, so the next call has the answer kept); `envrouter status` doesn't start a login shell, since nothing is kept between CLI runs, unless given `--agents` (then it waits up to 16 s, `SHELL_WAIT`, and `--json` carries `missingAgents`, the text an `Agents` line). The window applies only the latest `get_setup_status` answer (`setupSeq` in `useConfigStore`).
- **`check_folder` emulates a new terminal window** of the platform (`crates/core/src/platform.rs`): a cleared environment with the PATH that platform's terminals start with (`new_terminal_path`: macOS's bare one, `/etc/environment` on Linux, WSL's default plus its Windows folders) and the session's variables, and an interactive shell that's a login shell on macOS and WSL but not on a Linux desktop. The login shell comes from `$SHELL`, or `getent passwd` when an app started from a `.desktop` file has none. `-c` never draws a prompt, so the probe runs the prompt hooks once itself (zsh `chpwd`/`precmd`, bash `PROMPT_COMMAND`, fish `fish_prompt` events): mise and direnv reorder PATH there. When the shim was first before the hooks and isn't after, the result says `byPromptHook`. Output goes to temp files, not pipes, because prompt themes leave background jobs holding pipes open, and markers are matched anywhere in a line, because hooks and startup files print without newlines. It never runs the real tool. The shim's `ENVROUTER_EXPLAIN=1` mode reports the route instead.
- **The shim and the secrets helper are built by `crates/build-support`**, called from `src-tauri/build.rs` (and `crates/ops/build.rs`, whose tests install them), into `target/shim/` (inside `CARGO_TARGET_DIR` when set); the app's build stages them as `src-tauri/binaries/envrouter-{shim,keychain}-<triple>` for `bundle.externalBin`; the app installs both into `~/.envrouter/bin/` through a temp file and a rename (overwriting a signed binary in place gets it SIGKILLed). A child `dd` writes the temp file, never this process (`shims::install_file`, so the CLI's `install` too): the app forks all the time, and a child forked while the file is open for writing keeps that handle until it execs, which on Linux makes running the renamed file fail with ETXTBSY "Text file busy" (a lock around the app's own spawns wouldn't cover the libraries'). It's `dd`, not `cp`, because macOS's `cp` (with or without `-X`) and `ditto` copy the bundle's `com.apple.quarantine` onto the copy, which Gatekeeper would enforce on the unnotarized shim. That module is unix-only today; native Windows (M7) needs its own copy step. Anything else that must exec a file it wrote copies it with a child `dd` or `cp` the same way; ops tests call `shims::write_executable`. It's always built with the `helpers` profile (release with whole-program LTO and one codegen unit, kept for the binaries on every agent launch; `release` itself has thin LTO, parallel codegen and optimises for size, which builds the app and CLI twice as fast and downloads smaller), whatever the outer profile: every profile stages to that one file, so per-profile builds let `tauri build` bundle a debug shim. The macOS bundle is arm64-only for now; Intel support needs a universal build plus `lipo` of the shim. Linux builds also ship `envrouter-keychain.exe` (cross-compiled with mingw, built once per release by the `windows-helper` job and shared as an artifact; `.cargo/config.toml` links it without a PE timestamp, so the same source and toolchain give the same bytes) beside the shim, and `shims::install_bundled` installs it when it's there, for WSL. `shims::bundled` follows links, so a CLI linked into Homebrew's `bin` finds the helpers in its keg.
- **Icons are drawn as SVG** in `src-tauri/icons/`: `app-icon.svg` (128 px and up), `app-icon-small.svg` (a bolder cut for 64 px and under) and `tray.svg` (the menu bar template). Every PNG and `icon.icns` is rendered from them at its exact pixel size with a transparent background, the `.icns` through an `iconutil` iconset that takes the small cut for 16 to 64 px. Don't run `tauri icon`: it rebuilds every size from one source, losing the small cut, and recreates the Windows tiles. The tray image is a template, so macOS reads only its alpha; its cutouts must be mask transparency, not white fills. tray-icon draws it 18 pt tall whatever its size, so `tray.svg`'s viewBox hugs the glyph and `tray.png` is 36 px. Rendered PNGs carry their origin (`impeccable embed-prompt --read`).
- **Signing is ad hoc** (`bundle.macOS.signingIdentity: "-"`), so the bundle has a valid signature for the Mac that built it, and the hardened runtime is off. Turning it on would make dyld strip every `DYLD_*` variable from the shim's environment before it execs the real tool (verified). If it's ever needed, sign with an entitlements file containing `com.apple.security.cs.allow-dyld-environment-variables`; Tauri applies one file to the app and the shim alike.
- **Review the UI in a browser, never against the real home folder.** `pnpm dev` and then `http://localhost:1420/?scenario=first-run|populated|mcp|shadowed|broken` (add `&platform=linux` or `&platform=wsl` for those systems, and `&check=`, `&shim=stale` or `&store=off` for states a real machine can be in; docs/contributing.md lists them) runs the frontend with every Tauri call answered by `src/dev/mockTauri.ts` (dev-only; `window.__mockDrop(path, x, y)` simulates a Finder drop). Keep the mock answering as the real backend does, with fresh objects each call: a check in a shell that's off returns `shadowedOnPath`, not `notFound`, whenever the tool is installed. `src/dev/mockTauri.test.ts` pins the mock's answers that mirror backend messages. Running the real app touches `~/.envrouter`, and its shell toggles edit the real startup files. To try the real app safely, launch the built binary with `HOME` set to a scratch folder.
- **Wire types live in `src/lib/types.ts`.** Rust tests pin the JSON (`wire_format_matches_the_typescript_types` in `shell.rs` and `editors.rs`; the rpc envelope in `rpc.rs`), so change both sides together. Commands reject with a message string, except `get_config`, which rejects with a `ConfigFault` (`{ kind, message }`; over rpc the response carries `errorKind` beside `error`), because the window offers Back Up and Start Over only for a config.json that won't parse (`ErrorKind::Parse`), never by matching message text.
- **Check Linux and Windows from a Mac with `dev/containers/compose.yaml`** (Podman or Docker, project `envrouter-dev`): `linux-test` (backend tests with every shell required, and a GNOME Keyring round trip), `linux-app`, `linux-bundle` (the `.deb` and AppImage as the release builds them), `windows-helper-build` then `windows-helper-wine` (the Credential Manager round trip under Wine, a test-only Windows compatibility layer; only Wine runs emulated, since qemu crashes Rust tooling). The shell tests skip a missing shell, except under `ENVROUTER_REQUIRE_SHELLS=1`, which CI and the containers set.
- **`XDG_CONFIG_HOME` counts only inside the given home** (`platform::xdg_config_home`), so a test's scratch home can't reach the real config folder.
- `.claude/settings.json` denies Claude read access to `.env` files. Ask the user for variable names instead.
