# EnvRouter

@.claude/context/ai-context/docs-overview.md

EnvRouter is a macOS desktop app (Tauri v2) that does two things per folder for coding agents
(Claude Code and Copilot CLI): it sets the agent's config variable, so `claude`
run in `~/dev/work` uses a different `CLAUDE_CONFIG_DIR` than in `~/dev/personal`, and it hands
the agent a set of **MCP servers**. The user defines **profiles**: each one maps trigger folders to
a variable per tool and a selection from the MCP **server library**. Profiles are stored in `~/.envrouter/config.json`. Other macOS users get it as
source and build it themselves (README "Build and install"). There's deliberately no paid
Apple Developer ID, so no Developer ID signing, notarization or prebuilt downloads.

**How it works: shims, like mise or volta.** `~/.envrouter/shims/<tool>` is a symlink to
`~/.envrouter/bin/envrouter-shim`, a small Rust binary, and a marked block in the user's shell
startup files puts `shims/` first on PATH. On each run the shim reads `config.json`, picks the
profile for the current folder, sets that tool's variable, adds that profile's MCP servers to
the command line, and `exec`s the real tool found later on PATH. Config edits apply on the next
run in every terminal, with nothing to reload.

## How MCP servers reach an agent (`crates/core/src/mcp.rs`)
- **No gateway or daemon.** On every save the app renders, per profile and per agent with an MCP descriptor, one config file per server in the agent's dialect plus a `launch.json` manifest, under `~/.envrouter/mcp/<profile id>/<command>/` (files 0600, folder 0700). The shim reads only the manifest and adds its arguments ahead of the user's own.
- **Always the `--flag=value` form.** Claude's `--mcp-config` and `--disallowedTools` take several values, so `--mcp-config <file>` as two arguments swallows the next one (`claude --mcp-config f mcp --help` breaks; `--mcp-config=f mcp --help` works, verified on 2.1.303). `config::validate` rejects a descriptor without the `=`. `claude mcp list` never shows flag-injected servers. Copilot (verified on 1.0.98) takes `--additional-mcp-config=@<file>` (repeatable, added to the user's own servers) and turns a tool off with one `--deny-tool=<server>(<tool>)` per tool; `copilot mcp list` doesn't show injected servers either. Copilot expands `${VAR}` in env and headers, not args, so a Keychain secret belongs in an env var or header there.
- **Secrets live in one login-Keychain item** (`crates/keychain`), keyed by the canonical home folder, so scratch-HOME runs and tests never see the real one. Rendered files refer to `${ENVROUTER_SECRET_<ID>}`. **The shim never links the Security framework**: loading it cost ~1.4 ms on every launch (measured), so the shim runs the `envrouter-keychain read <ids>` helper, installed beside it, only when a server needs a secret (20s timeout), reads the values from its stdout and sets them on the agent. Keep `crates/core` and `crates/shim` free of `security-framework`; `otool -L` on the release shim should list only `libSystem`. Secret values are never in argv, `config.json` or a rendered file. Typed values travel only with `save_config(payload, secrets)`, which stores them (and prunes unreferenced ones) before writing the config, and reads the Keychain only when a save adds or drops a secret; the window never gets a value back. After installing a new helper while secrets are in use (on save, or at launch after an update), the app runs `envrouter-keychain read` once, so macOS asks for access while the app is in front.
- **Checking a server** (`src-tauri/src/mcp_probe.rs`, on the official `rmcp` crate) runs only when the user clicks: it starts the server with the login shell's PATH (`shell::login_path`, since a Finder-launched app has a bare one), lists its tools, and stops it. Tool lists from good checks are cached in `~/.envrouter/mcp-tools.json` with the definition they came from, and only offered while it matches. rmcp has no legacy SSE client, so SSE servers report `unsupported`. Tool filtering is a deny list (`disabledTools`), rendered for Claude as `--disallowedTools=mcp__<server>__<tool>`.
- **Import only reads** (`src-tauri/src/mcp_import.rs`): each agent's own MCP files, located by its `mcpFiles` descriptor in `tools.ts` (Claude: `.claude.json` in `~` and each profile's config folder, including its `projects` tables, plus `.mcp.json` in trigger folders). Credential-looking values (`SECRET_NAME` in `src/lib/mcp.ts`) are moved to the Keychain on import; `${VAR}` references stay as typed. The catalog (`src/lib/mcpCatalog.ts`) is written from each vendor's README.
- A profile's servers go to every agent with a descriptor, even if the profile leaves that agent's folder alone, so `config::tool_names` gives those agents shims too.

The window is built around a direction called **the Sorting Frame**: one card per profile
with its folders filed inside, rendered as modern layered Mac cards (the user asked for
clearly separated surfaces, so don't regress to flat ruled grids). Before changing the UI, read `PRODUCT.md` and
`.impeccable/surfaces/src-app-tsx.md` (the direction contract), and `DESIGN.md` (tokens and
rules: one accent button per state, status-free profile colours, the editor is a right-side
inspector). The app also lives in the menu bar (`src-tauri/src/tray.rs`), and closing the window
only hides it.

## How routing resolves (`crates/core/src/resolve.rs`)
- **The most specific profile wins outright.** The deepest trigger containing the folder picks the profile. If that profile doesn't configure the tool, the tool runs with **no** override; it never falls back to a shallower profile. The user chose this deliberately.
- **Compare canonical paths, never `$PWD` text.** `$PWD` keeps typed symlinks and letter case (`~/Dev` on a case-insensitive volume), so both the folder and each trigger go through `fs::canonicalize`.
- **Triggers are whole-subtree prefixes.** `~` is expanded and a trailing `/*` or `/**` is dropped (`config::trigger_base`); any other `*` is rejected. `config.json` keeps what the user typed.
- **`config::validate` runs on every save.** It rejects a folder claimed by two profiles, tool or env var names that aren't strict identifiers, and a tool folder that isn't absolute or `~`-based (a relative one would resolve against wherever the tool runs; `resolve` skips one from a hand-edited config too). Tool names become file names in `shims/` and are interpolated into shell probes, so keep `is_command_name` strict.

## The shim must never block the tool
A missing config means the tool runs silently. A broken one prints a warning and the tool still runs. The same goes for MCP: no manifest means no injection, a broken one warns, a server whose secret can't be read is left out with a warning, `--strict-mcp-config` (or `ENVROUTER_MCP=0`) turns injection off for that run, and explaining never asks the Keychain. When looking for the real binary, the shim skips the shims directory, empty PATH entries (the current directory), and anything that canonicalizes to itself, so it can never exec itself in a loop. Keep these properties; `crates/shim/tests/shim.rs` covers each one.

## Constraints
- **No logins or OAuth.** EnvRouter never signs anyone into an agent or an MCP server; agents run their own sign-in (`/mcp`). The one credential it handles is MCP secret values the user enters, kept in the Keychain item above.
- **Tauri v2 APIs only.** v1 examples (`tauri.conf.json > allowlist`, `@tauri-apps/api/fs`) are wrong here. Use plugins and `capabilities/*.json`.
- **All file access happens in Rust commands.** There's deliberately no fs plugin, and `capabilities/default.json` grants only the three plugin calls the window makes (dialog open, dialog message, opener reveal), one by one. Don't go back to a plugin's `:default` set, and don't add `@tauri-apps/plugin-fs` back.
- **The window has a CSP** (`app.security.csp` in `tauri.conf.json`): scripts and styles from the bundle only, and IPC. Loading anything remote or adding an inline script means changing the policy on purpose.
- **Keep the data model tool-agnostic.** `Profile.tools` is a `Record<toolName, { envVar, path }>`. Nothing in Rust branches on an agent's name: agent behaviour is data in `src/lib/tools.ts` (its variable, and an MCP descriptor naming a config *dialect*, a file format), which the window writes into `config.agents` on every save. Rust renders dialects, not agents. Add an agent with one entry in `src/lib/tools.ts`, and only after checking its docs: the variable must relocate logins too, not just settings; note quirks in the entry's `note`. A config that still names an agent the window no longer offers keeps loading, saving and routing. `save_config` creates missing agent folders inside home. Codex and Gemini CLI were dropped to keep the app focused; they're future add-ons (Codex: `-c mcp_servers.*` overrides with secrets through `env_vars`, and its MCP OAuth tokens are shared across `CODEX_HOME`s; Gemini: settings in a file named by `GEMINI_CLI_SYSTEM_DEFAULTS_PATH`, which shallow-merges `mcpServers`, and `GEMINI_CLI_HOME` holds a `.gemini` folder).
- **Bump `CONFIG_VERSION` in `config.rs`** for any change to the shape of `config.json`, and migrate older versions in `config::load`. The shim refuses configs from a newer version.

## Conventions
- **pnpm only.** `packageManager` pins `pnpm@12.10.1`, and `devEngines` downloads it if it's missing.
- **Biome, not ESLint or Prettier:** 2-space indentation, **single quotes, no semicolons**, 150-column lines. Don't copy the double-quote/semicolon style from Tauri docs. Run `pnpm format-and-lint:fix`.
- **Tailwind v4** through `@tailwindcss/vite`: no config file and no PostCSS; theme tokens go in `src/index.css` with `@theme`.
- **Rust is a Cargo workspace** rooted at the repo (`crates/core`, `crates/keychain`, `crates/shim`, `src-tauri`), with one `target/` at the root. Use `cargo fmt --all`. Release profile settings live in the root `Cargo.toml`.
- **Rust tooling:** `rust-toolchain.toml` pins 1.99.0 (rustup reads it; Homebrew Rust doesn't, so match it by hand). `[workspace.lints]` forbids `unsafe` and adds a curated slice of clippy pedantic; every member opts in with `[lints] workspace = true`. `cargo deny check` (`deny.toml`) allows permissive licences only, so no GPL code can arrive through a dependency, and checks RustSec advisories. `cargo machete` finds unused dependencies. CI runs all of them.

## Gotchas
- **Tests must never touch the real home directory.** Shell code resolves startup files from the `home` it's given, and finds zsh's `ZDOTDIR` by asking a fresh zsh, never from the process environment. Don't read `ZDOTDIR` or `HOME` from `std::env` in testable code. Claude Code's own environment sets `ZDOTDIR`.
- **The shell block is POSIX sh** (`shell.rs`, `POSIX_BODY`), so it's safe when bash's login file is `.profile`. It moves the shims directory to the front of PATH rather than skipping it when it's already there, because nested shells re-prepend `~/.local/bin`.
- **`check_folder` emulates a new Terminal window,** with a cleared environment and a login, interactive shell. `-c` never draws a prompt, so the probe runs the prompt hooks once itself (zsh `chpwd`/`precmd`, bash `PROMPT_COMMAND`, fish `fish_prompt` events): mise and direnv reorder PATH there. When the shim was first before the hooks and isn't after, the result says `byPromptHook`. Output goes to temp files, not pipes, because prompt themes leave background jobs holding pipes open, and markers are matched anywhere in a line, because hooks and startup files print without newlines. It never runs the real tool. The shim's `ENVROUTER_EXPLAIN=1` mode reports the route instead.
- **`src-tauri/build.rs` builds the shim and the Keychain helper** into `target/shim/` and stages them as `src-tauri/binaries/envrouter-{shim,keychain}-<triple>` for `bundle.externalBin`; the app installs both into `~/.envrouter/bin/` through a temp file and a rename (overwriting a signed binary in place gets it SIGKILLed). It's always a release build, whatever the profile: every profile stages to that one file, so per-profile builds let `tauri build` bundle a debug shim. The bundle is arm64-only for now; Intel support needs a universal build plus `lipo` of the shim.
- **Icons are drawn as SVG** in `src-tauri/icons/`: `app-icon.svg` (128 px and up), `app-icon-small.svg` (a bolder cut for 64 px and under) and `tray.svg` (the menu bar template). Every PNG and `icon.icns` is rendered from them at its exact pixel size with a transparent background, the `.icns` through an `iconutil` iconset that takes the small cut for 16 to 64 px. Don't run `tauri icon`: it rebuilds every size from one source, losing the small cut, and recreates the Windows tiles. The tray image is a template, so macOS reads only its alpha; its cutouts must be mask transparency, not white fills. tray-icon draws it 18 pt tall whatever its size, so `tray.svg`'s viewBox hugs the glyph and `tray.png` is 36 px. Rendered PNGs carry their origin (`impeccable embed-prompt --read`).
- **Signing is ad hoc** (`bundle.macOS.signingIdentity: "-"`), so the bundle has a valid signature for the Mac that built it, and the hardened runtime is off. Turning it on would make dyld strip every `DYLD_*` variable from the shim's environment before it execs the real tool (verified). If it's ever needed, sign with an entitlements file containing `com.apple.security.cs.allow-dyld-environment-variables`; Tauri applies one file to the app and the shim alike.
- **Review the UI in a browser, never against the real home folder.** `pnpm dev` and then `http://localhost:1420/?scenario=first-run|populated|shadowed|broken` runs the frontend with every Tauri call answered by `src/dev/mockTauri.ts` (dev-only; `window.__mockDrop(path, x, y)` simulates a Finder drop). Keep the mock answering as the real backend does, with fresh objects each call: a check in a shell that's off returns `shadowedOnPath`, not `notFound`, whenever the tool is installed. Running the real app touches `~/.envrouter`, and its shell toggles edit the real startup files. To try the real app safely, launch the built binary with `HOME` set to a scratch folder.
- **Wire types live in `src/lib/types.ts`.** A Rust test (`wire_format_matches_the_typescript_types` in `shell.rs`) pins the JSON, so change both sides together.
- `.claude/settings.json` denies Claude read access to `.env` files. Ask the user for variable names instead.
